## 환경
- 실행 환경: 로컬 macOS (KST, UTC+9)
- 데이터베이스: H2 In-Memory DB (기본 UTC로 동작)
- 테이블 정의: issue_date 컬럼이 date 타입으로 정의되어 있음.

```sql
create table footstep (
    issue_date date not null,
    ...
)
```

## 이슈 현상

- FakeClockHolder를 이용해 날짜를 2025년 5월 24일로 고정한 뒤, 발자취(Footstep)를 생성하고 저장. 
- 하지만 저장된 엔티티를 다시 조회했을 때, issue_date 필드가 하루 전인 2025년 5월 23일로 조회되어 테스트가 실패.

```kotlin
// ...
val clockHolder = FakeClockHolder(localDate = LocalDate.of(2025, 5, 24))
val actual = SUT.createFootstep(request)

// then
// 여기서 actual.date가 2025-05-23으로 나와 테스트 실패
assertThat(actual.date).isEqualTo(LocalDate.of(2025, 5, 24))
```



## 원인 분석

- 문제의 핵심은 테스트를 실행하는 환경(KST)과 DB(UTC)의 시간대가 달라 발생한 변환 오류 
- 테스트 코드에서 타임존 정보가 없는 LocalDate 객체(2025-05-24)를 생성 
- JPA(Hibernate)는 이 객체를 DB에 저장하기 위해, **테스트 JVM의 기본 타임존(KST)**을 기준으로 "한국의 5월 24일 0시" (2025-05-24 00:00:00 KST)로 해석 
- JDBC 드라이버는 이 시간을 **DB의 타임존(UTC)**에 맞춰 변환했습니다. 그 결과, "한국 24일 0시"는 UTC로는 하루 전인 "2025-05-23 15:00:00 UTC"가 되었음. 
- 결론적으로 issue_date 컬럼에는 5월 23일에 해당하는 값이 저장되었고, 조회 시에도 동일하게 23일로 반환되어 문제가 발생.



## 해결 ✅

- 테스트 실행 환경 자체를 UTC로 강제하여, JVM과 DB의 시간대를 일치
- build.gradle.kts 파일에 아래 코드를 추가하여 테스트 JVM의 타임존을 UTC로 설정


```groovy
tasks.withType<Test> {
    useJUnitPlatform()
    systemProperty("user.timezone", "UTC")
}
```

- 이 설정으로 인해 LocalDate를 해석하고 변환하는 모든 과정이 UTC 기준으로 통일되어 문제가 해결
