# API 통합 테스트와 단위 테스트의 역할

API를 제공하는 애플리케이션에서는 내부 구조를 리팩터링하더라도 기존 API가 동일하게 동작한다는 것을 보장해야 한다.

API 레벨의 테스트는 사용자에게 보이는 동작과 외부 계약을 보호하고, 단위 테스트는 내부의 비즈니스 규칙과 유즈케이스를 빠르고 세밀하게 검증한다.

> API 테스트로 "사용자에게 보이는 동작이 유지된다"를 보장하고, 단위 테스트로 "왜 그렇게 동작하는지"를 촘촘하게 보장한다.

## 테스트의 역할 구분

### API 통합 테스트

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class SomeApiIntegrationTest {
}
```

실제 엔드포인트로 HTTP 요청을 보내고, Spring Context에 등록된 구성요소들이 함께 동작하는지 검증한다.

```text
HTTP 요청
 → Filter·Security
 → Controller
 → 입력 포트
 → 응용 서비스
 → 출력 포트
 → DB 어댑터
 → HTTP 응답
```

API 통합 테스트는 다음을 보장하는 회귀 테스트 역할을 한다.

- Spring Bean과 의존성이 올바르게 연결되는가?
- 요청이 올바른 엔드포인트로 라우팅되는가?
- 인증·인가와 요청 검증이 동작하는가?
- 요청과 응답이 올바르게 직렬화되는가?
- 요청부터 응답까지 전체 흐름이 동작하는가?
- 트랜잭션과 영속성 처리가 기대한 대로 동작하는가?
- 예외가 약속된 상태 코드와 응답으로 변환되는가?
- 내부 구조를 변경해도 기존 API 계약이 유지되는가?

API 통합 테스트에는 모든 세부 조건을 넣기보다 대표적인 흐름을 둔다.

- 정상 요청 → `200 OK` 또는 `201 Created`
- 잘못된 요청 → `400 Bad Request`
- 대상을 찾을 수 없음 → `404 Not Found`
- 핵심 비즈니스 조건 위반 → 약속한 오류 응답

응용 서비스나 입력 포트를 Mock으로 대체한 Controller 단독 테스트는 이 전략에서 별도 계층으로 두지 않는다. Controller가 대부분 요청을 변환하고 입력 포트를 호출하는 역할만 한다면, 구현 호출 여부를 검증하는 테스트보다 실제 엔드포인트를 통과하는 API 통합 테스트가 더 직접적인 안전망이 된다.

외부 결제 API나 메시지 브로커처럼 테스트에서 실제로 실행하기 어려운 경계만 Fake 또는 Stub으로 대체할 수 있다. 이때도 Controller, 응용 서비스, 도메인 로직과 내부 DB 어댑터는 가능한 한 실제 구성을 사용한다.

### 유즈케이스 단위 테스트

유즈케이스가 포트 인터페이스에 의존한다면 Spring Context 없이 응용 서비스를 직접 생성할 수 있다.

```java
@ExtendWith(MockitoExtension.class)
class SomeUseCaseTest {

    @Mock
    private LoadSomethingPort loadSomethingPort;

    @Mock
    private SaveSomethingPort saveSomethingPort;

    private SomeUseCaseService service;

    @BeforeEach
    void setUp() {
        service = new SomeUseCaseService(
            loadSomethingPort,
            saveSomethingPort
        );
    }
}
```

이 테스트에서는 다음을 확인한다.

- 필요한 객체를 올바르게 조회하는가?
- 도메인 객체의 적절한 행위를 호출하는가?
- 조건에 따라 올바른 출력 포트를 호출하는가?
- 실패 조건에서 처리를 중단하는가?
- 유즈케이스의 실행 순서와 분기가 올바른가?

`MockitoExtension`은 Spring을 실행하지 않는다. JUnit에서 Mockito의 Mock 객체만 만들어주므로 테스트 실행이 빠르다.

서비스를 직접 생성하면 Spring 프록시가 없으므로 `@Transactional`은 동작하지 않는다. 단위 테스트에서는 유즈케이스의 흐름을 검증하고, 실제 트랜잭션 동작은 API 또는 영속성 통합 테스트에서 검증한다.

### 도메인 단위 테스트

애그리거트, 엔티티, 값 객체, 도메인 서비스의 순수한 비즈니스 규칙을 검증한다.

- 경계값
- 허용되는 상태 변경
- 금지되는 상태 변경
- 계산 규칙
- 도메인 불변식

세부적인 비즈니스 조건은 실행 비용이 큰 API 통합 테스트보다 도메인 단위 테스트에서 촘촘하게 확인한다.

## 권장 테스트 구성

```text
소수의 API 통합 테스트
└── 전체 연결과 외부 API 계약 보장

필요한 Adapter 통합 테스트
└── 복잡한 JPA 매핑과 외부 연동 구현 검증

다수의 유즈케이스·도메인 단위 테스트
└── 비즈니스 규칙, 경계값, 실행 흐름과 분기 검증
```

| 테스트 | 주된 목적 | Spring Context | 테스트 개수 |
|---|---|---:|---:|
| API 통합 테스트 | 전체 흐름과 API 계약 보장 | 사용 | 소수 |
| Adapter 통합 테스트 | DB 및 외부 연동 구현 검증 | 필요에 따라 사용 | 적당히 |
| 유즈케이스 단위 테스트 | 응용 흐름과 포트 호출 검증 | 사용하지 않음 | 다수 |
| 도메인 단위 테스트 | 순수 비즈니스 규칙 검증 | 사용하지 않음 | 다수 |

## 리팩터링할 때의 활용

기존 구조를 헥사고날 아키텍처로 변경한다면 API 통합 테스트를 먼저 안전망으로 확보한다.

```text
1. 기존 API의 대표적인 정상·실패 동작을 통합 테스트로 고정한다.
2. 내부 구조를 포트와 어댑터로 분리한다.
3. 분리된 유즈케이스와 도메인 규칙에 단위 테스트를 추가한다.
4. API 통합 테스트를 다시 실행해 외부 동작이 유지되는지 확인한다.
```

API 통합 테스트만으로 모든 조건을 검증하면 테스트가 느리고 실패 원인을 찾기 어렵다. 반대로 단위 테스트만 있으면 실제 Spring 설정과 HTTP, DB 연결의 오류를 발견하지 못할 수 있다.

따라서 두 테스트는 서로 대체하는 관계가 아니라 서로 다른 위험을 보완하는 관계다.

> 외부 계약은 API 통합 테스트로 보호하고, 내부 규칙은 빠른 단위 테스트로 보호한다.
