## SpringBootTest 써도 될까?

출처: 토비의 스프링 디스코드

> 클린 스프링 강의를 90%정도 들었는데... 테스트를 작성하실때 도메인테스트 외에는 application쪽은 @SpringBootTest 띄워서 통합테스트로 작성하시더라구요... 저는 테스트는 빠른게 좋다고 다른 강의에서 배워서 지금까지 그런줄로 알고 있었는데, 혹시 그게 아닌걸까요? 어떤게 맞는건지 잘 모르겠네요..😥  그리고 절차지향적 설계에서는 서비스 레이어에 로직이 있으니까 테스트 코드 작성할때, 그 부분을 테스트하면 될거 같은데 이런 도메인 모델 설계는 어플리케이션 서비스에서 뭘 테스트 하면 좋을까요???  테스트가 의미가 있나 싶기도 합니다..

> @SpringBootTest는 충분히 빠릅니다. 그래서 쓰는 거고요.
> 
> 만약 이걸 단위 테스트로 만든다고 Repository등을 비롯해서 의존하는 오브젝트를 다 목을 만들거나  아니면 완료되어서 상태 변화까지 검증하는 테스트로 만들려면 테스트 "작성" 속도가 느려집니다. 테스트 수행 속도보다 작성 속도가 중요해요. 
> 
> @SpringBootTest하나 Mockito Test하나 속도는 전체 다 돌릴 때 테스트 100개 기준으로 2-3초 차이나지만, 테스트 작성이 어려우면 테스트 많이 못 만듭니다. 테스트 때문에 개발 속도 느려지고, 테스트에 버그가 들어가죠. 그래서 성능+생산성을 다 고려하면 @SpringBootTest가 필요한 경우엔 그걸 씁니다.
하루에 테스트 1000개를 30번 돌린다고 했을 때 @SpringBootTest를 썼기 때문에 매번 5초가 더 걸린다고 해도. 150초. 3분도 더 안 걸립니다.
> 
> 하지만 @SpringBootTest를 안 만들기 위해서 테스트를 복잡하게 만드느라 추가로 걸리는 시간 1시간이라면.
도메인 모델이 있는 경우에는 도메인 로직의 검증이 이미 도메인 테스트에서 끝났으므로, 애플리케이션 테스트에서는 서비스 계층이 도메인과 외부 서비스(DB등)와 잘 결합해서 결과가 나오는지, 혹은 서비스 레벨의 로직(개발 방법에 따라 검증 또는 로직에 따른 라우팅, 이벤트 발생, 외부 서비스 호출)이 잘 동작하는지만 간단하게 체크하면 됩니다. 도메인 테스트에서 했던 모든 테스트를 다시 반복할 필요는 없죠.
