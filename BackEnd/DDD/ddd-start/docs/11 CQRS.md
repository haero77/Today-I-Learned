# 11.1 단일 모델의 단점

- 주문 내역 조회 기능 구현 시, 여러 애그리거트에서 데이터 가져와야함. 
- 간접 참조(식별자를 이용한 애그리거트 참조) 방식 사용 시, eager loading과 같은 JPA의 쿼리 관련 최적화 기능 사용 불가.
  - 👉한 번의 SELECT 쿼리로 화면에 필요한 데이터를 읽어올 수 없으므로 조회 성능에 문제 발생 가능.
- 직접 참조 방식도 마찬가지로 고민이 생김.
  - 조회 하면 특성에 따라 같은 연관도 즉시 로딩 또는 지연 로딩으로 처리해야하기 때문.

## 객체 지향 도메인 모델

- ORM 기법은 `order.cancel`, `order.changeShippingInfo`와 같은 도메인 상태 변경 기능을 구현하는데 적합.
- 그러나, 주문 상세 조회 화면처럼 여러 애그리거트에서 데이터를 가져왕 출력하는 기능을 구현하기에는 고려할 게 많아서 구현을 복잡하게 만드는 원인이 된다.
- 상태 변경용 모델과 조회를 위한 모델을 분리함으로써 복잡도 감소 가능.

# 11.2 CQRS

## 11.2 CQRS

### 시스템이 제공하는 두 가지 기능 

- 도메인 모델 관점에서, **상태 변경 기능은 주로 한 애그리거트의 상태를 변경**
- 상태 조회 기능은 주로 두 개 이상의 애그리거트가 필요.
- 상태 변경 범위와, 상태 조회 **범위가 정확하게 일치하지 않기 때문에** 단일 모델로 두 종류 기능 구현 시 모델이 불필요하게 복잡해짐.

### CQRS는 복잡한 도메인에 적합

- 도메인이 복잡할수록 명령 기능과 조회 기능이 다루는 데이터 범위에 차이가 난다.
- 두 기능 단일 모델 처리 시 조회 기능의 로딩 속도를 위해 모델 구현이 필요 이상으로 복잡해짐.
- (예) 주문/판매 통계 기능을 구현한다고 할 때, 
  - JPA 기반 단일 도메인 모델을 사용하면 통계값을 빠르게 조회하기 위해 JPA 관련된 성능 기능을 모델에 적용해야함.
  - 위 같은 도메인에 CQRS 적용 시, 통계를 위한 조회 모델을 따로 만들기 때문에 조회 기능 때문에 도메인 모델이 복잡해지는 것은 막을 수 있음.

### CQRS: 각 모델에 맞는 기술 구현 가능

- 명령 모델: 객체 지향에 기반에서 도메인 모델을 구현하므로 JPA 사용해서 구현.
- 조회 모델: DB 테이블에서 SQL로 데이터 조회할 때 좋은 마이바티스를 사용해서 구현.

### CQRS 사용 시 아키텍처

- 명령: 컨트롤러 -> 응용 서비스 -> 도메인 -> 인프라(JPA 리포지터리 구현) -> DB
- 조회: 컨트롤러 -> DTO/DAO -> 인프라(MyBatis: DAO 구현) -> DB

---

- 조회 기능에서는 응용 서비스가 없다.
  - 조회 기능은 응용 로직이 복잡하지 않으므로, 컨트롤러에서 DAO 바로 실행해도 무방.
  - 데이터 표현 영역에 몇 가지 로직 필요한 경우에는 응용 서비스를 두고 로직을 구현하면 됨.

### 명령/조회 모델이 다른 데이터 저장소 사용하는 경우

- 명령 모델을 트랜잭션을 지원하는 RDBMS, 조회 모델은 조회 성능이 좋은 NoSQL을 사용해서 구현 가능.
- 두 데이터 저장소 간 데이터 동기화는 이벤트를 활용해서 처리.
- 명령 모델에서 데이터 바뀌자 마자 변경 내역을 조회 모델에 적용해야하는 경우 👉동기 이벤트와 글로벌 트랜잭션 사용하여 실시간 동기화 (성능은 떨어짐)
- 서로 다른 저장소를 특정 시간 안에만 동기화하면 되는 경우
  - 비동기로 데이터 전송.

## 11.2.1 웹과 CQRS

> _**조회 속도를 높이기 위해 별도 처리를 하고 있다면 명시적으로 명령 모델과 조회 모델을 분리하자.**_

- 일반적인 웹 서비스의 경우 요청보다 상태를 조회하는 요청이 훨씬 많ㅇ므.
- 조회 성능 최적화를 위해, 쿼리 최적화, 메모리에 조회 데이터 캐싱 등 다양한 방법을 사용.
- 조회 성능을 높이기 위해 다양한 기법을 사용하는 것을 실질적으로 CQRS를 적용하는 것과 같은 효과
- _**조회 속도를 높이기 위해 별도 처리를 하고 있다면 명시적으로 명령 모델과 조회 모델을 분리하자.**_
  - 조회 기능 때문에 명령 모델이 복잡해지는 것을 방지 가능.
  - 명령 모델에 관계없이 조회 기능에 특화된 구현 기법을 보다 쉽게 적용 가능.

## 11.2.2 CQRS 장단점

### 장점

1. 명령 모델 구현 시 도메인 자체에 집중 가능.
2. 조회 성능 향상에 유리.
   1. 조회 단위로 캐시 적용, 조회에 특화된 쿼리 등.. 

### 단점

1. 구현해야할 코드가 더 많다.
   1. 도메인 복잡하거나, 대규모 트래픽 있는 서비스라면 조회 전용 모델을 만드는게 유리. 
   2. but 도메인 단순하거나 트래픽 많지 않다면 조회 전용 모델을 만들어서 얻는 이점이 뭔지 따져봐야함.
2. 더 많은 구현 기술 필요
   1. 명령/조회 모델 다른 구현 기술 적용 가능. 서로 다른 저장소 사용 가능
   2. 데이터 동기화를 위해 메시징 시스템 도입해야할 수도 ㅣㅇㅆ음.

### 결론

- **_도메인이 복잡하지 않으면 CQRS 적용하지 말자._**
- 도메인이 복잡하지 않은데 CQRS 적용하면 두 모델을 유지하는 비용만 높아지고 얻을 수 있는 이점이 없음. 
  - but 트래픽 높은 서비스인데 단일 모델 고집하면 오히려 유지 보수 비용이 높아질 수 있으므로 이 경우 CQRS 적용 고려.
