# 들어가며

- 이 책의 목표 아키텍처에서는 외부 세계와의 모든 통신이 어댑터를 통해 이뤄짐.
- 이번 장에서는 그러한 웹 인터페이스를 제공하는 어댑터를 어떻게 구현할지 살펴봄.

# 의존성 역전

## 어댑터와 유스케이스 사이에 포트가 존재하는 이유

1. 포트가 곧 외부 세계가 애플리케이션 코어와 상호작용할 수 있는 장소들에 대한 명세이기 때문.
2. 포트가 있으면 외부 세계와 어떤 통신이 일어나는지 '정확히' 알 수 있고, 레거시 코드베이스를 작업하는 모든 유지보수 개발자에게 중요한 정보가 됨.

## 웹소켓을 구현하는 경우

- WebSocket 컨트롤러는 인커밍포트를 의존하면서, 동시에 아웃 포트를 구현함.

# 웹 어댑터의 책임

## 웹 어댑터가 실제로 하는 일

1. 들어오는 HTTP 요청을 객체로 매핑한다.
2. 인가 검사를 수행한다.
3. 입력을 검증한다.
4. 요청 객체를 유스케이스의 입력 모델로 매핑한다.
5. 유스케이스를 호출한다.
6. 유스케이스의 출력을 HTTP로 다시 매핑한다.
7. HTTP 응답을 반환한다.

## 웹 어댑터의 입력 모델의 검증

- 유스케이스에 대한 입력 모델에서 이미 수행한 것과 동일한 검증을 어댑터 입력모델에서 구현하는 것을 권장하지 않음.
- 대신 웹 어댑터의 입력 모델을 유스케이스 입력 모델로 변환할 수 있음을 검증해야하며, 이러한 변환 작업을 방해하는 것은 검증 오류임.
  - 즉, 웹 어댑터는 HTTP 요청값이 유스케이스 입력 모델의 타입으로 변환 가능한지를 검증함.
    - 예: 계좌 ID가 숫자인지, 금액이 `Money`로 변환 가능한 형식인지, 날짜나 enum 값의 형식이 올바른지.
  - 변환된 값 자체가 유스케이스의 입력 조건을 만족하는지는 유스케이스 입력 모델에서 검증함.
    - 예: `"-5000"`은 숫자이므로 `Money`로 변환할 수 있지만, 이체 금액은 0보다 커야 하므로 `SendMoneyCommand`에서 거부함.
  - 도메인의 현재 상태를 확인해야 하는 규칙은 유스케이스나 도메인 모델에서 검증함.
    - 예: 출금 계좌에 이체할 수 있는 충분한 잔액이 있는지.
  - 정리하면 `HTTP 형식 및 변환 가능 여부 → 웹 어댑터`, `유스케이스 입력값의 유효성 → 입력 모델`, `현재 상태에 따른 비즈니스 규칙 → 유스케이스 또는 도메인 모델`로 책임을 나눔.
