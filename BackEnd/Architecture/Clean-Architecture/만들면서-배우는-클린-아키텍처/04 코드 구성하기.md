# 계층별 구성

```
buckpal
├── domain
│   ├── Account
│   ├── Activity
│   ├── AccountRepository
│   └── AccountService
├── persistence
│   └── AccountRepositoryImpl
└── web
    └── AccountController
```

- 의존성 역전 원칙을 적용해 domain 패키지의 도메인 코드에 대해서만 의존성을 허용. 
  - (domain 패키지에 AccountRepository 인터페이스 도입하고, persistence 패키지에서 이를 구현)

## 계층별 구성이 최적이 아닌 이유 3가지

1. 애플리케이션 기능 간 패키지 경계가 없음.
   - 예를 들어 사용자 기능 추가할 경우 web 패키지에 UserController, domain 패키지에 UserService, UserRepository, User를, persistence 패키지에 UserRepositoryImpl을 추가해야함.
   - 특별한 구조없이는 다수 클래스로 혼잡해져서 애플리케이션 기능 들 사이에 원치 않는 부수효과 발생 가능.
2. 애플리케이션에서 제공하는 유즈케이스 파악 불가.
   - AccountService, AccountController 클래스가 어떤 유스케이스를 제공하는지 파악 불가.
   - 특정 기능을 찾을 시, 어떤 서비스가 그것을 구현하는지 추측한다음, 해당 서비스 내에서 메서드를 찾아야함.
3. 패키지 구조 내에서, 목표로 하는 아키텍처 파악 불가.
   - 그저 헥사고날 아키텍처 스타일을 따랐다고 짐작하고 나서 web, persistence 패키지 둘러 보면서 웹 및 영속성 어댑터를 찾을 뿐.임. 
   - 웹 어댑터가 어느 기능을 호출하고, 영속성 어댑터가 도메인 계층에 어떤 기능을 제공하는지 한눈에 파악 불가.
     - *인커핑 포트와 아웃고잉 포트가 코드에 숨겨져 있기 때문.

# 기능별 구성

```
buckpal
└── account
    ├── Account
    ├── SendMoneyController
    ├── AccountRepository
    ├── AccountRepositoryImpl
    └── SendMoneyService
```

- 계좌와 관련된 모든 코드를 상위 패키지 account 패키지에 모아두고 계층 패키지는 삭제
- 외부에서 접근하면 안 되는 클래스에 대해 package-private 가시성 부여하여 패키지 경계 강제.
  - 기능들 간에 원치 않는 의존성 발생 방지.
- AccountService -> SendMoneyService로 이름 변경하여 책임 범위를 좁힘.
  - 클래스명만 봐도 `자금 이체` 유즈케이스를 구현한다는 사실을 알 수 있음.
  - 이처럼 코드에서 애플리케이션의 기능을 보이게 만드는 것을 로버트 마틴은 소리치는 아키텍처라고 부름.

## 기능별 구성의 단점

- 기능별 패키지 접근법은 계층별 패키지 접근법에 비해 아키첵처의 가시성을 떨어뜨림. 
- 어댑터를 식별할 패키지명이 없고, 여전히 인커밍 포트와 아웃고잉 포트를 볼 수 없음.
- SendMoneyService가 AccountRepository 인터페이스에 의존하도록 하여 의존성의 방향은 올바르게 만들었지만, 도메인 코드와 영속성 코드가 같은 패키지에 있기 때문에 도메인 코드가 실수로 AccountRepositoryImpl 같은 영속성 구현체를 직접 사용하는 것을 막을 수 없음.

# 아키텍처적으로 표현력 있는 패키지 구조 

```
buckpal
├── adapter
│   ├── in
│   │   └── web
│   │       └── SendMoneyController
│   └── out
│       └── persistence
│           ├── AccountPersistenceAdapter
│           └── SprintDataAccountRepository
├── application
│   ├── domain
│   │   ├── model
│   │   │   └── Account
│   │   └── service
│   │       └── SendMoneyService
│   └── port
│       ├── in
│       │   └── SendMoneyUseCase
│       └── out
│           └── UpdateAccountStatePort
└── common
```

- 헥사고날 아키텍처의 주요 요소
  - 엔티티
  - 유스케이스
  - 입력/출력 포트
  - 인커밍/아웃고잉 어댑터
- 아키텍처의 각 요소를 패키지 중 하나에 직접적으로 매핑 가능. 최상위 수준에는 adapter, application 패키지 존재.
- adapter 패키지
  - 애플리케이션 인커밍 포트를 호출하는 인커밍 어댑터
  - 애플리케이션의 아웃고잉 포트를 구현하는 아웃고잉 어댑터

## 어댑터의 코드를 자체 패키지로 두는 이점: 변경에 대한 애플리케이션 격리

- **_외부 기술에 관한 코드를 어댑터 패키지에 격리하면, 애플리케이션의 핵심 로직을 변경하지 않고 DB나 외부 시스템의 구현체를 쉽게 교체할 수 있다. (애플리케이션이 격리됨)_**
- 어댑터의 코드를 자체 패키지로 두면 필요 시 하나의 어댑터를 다른 구현체로 매우 쉽게 교체할 수 있다는 이점 존재.
    - 어떤 데이터 접근 패턴이 필요해서 간단한 키-값 데이터베이스에 대한 영속성 어댑터를 구현했다가 해당 패턴이 바뀌어서 이제 SQL 데이터베이스가 더 적절한 상황이 되었다고 가정.
    - 이 때 새로운 어댑터 패키지에서 모든 관련 아웃고잉 포트를 구현한 다음, 이전 패키지를 제거하기만 하면 된다.

### 예시: Redis 어댑터를 SQL 어댑터로 교체하기

처음에는 Redis를 사용하기 위해 관련 코드를 하나의 어댑터 패키지에 모아 둔다.

```text
adapter/out/persistence/redis
├── RedisAccountPersistenceAdapter
├── RedisAccountEntity
└── RedisAccountRepository
```

`RedisAccountPersistenceAdapter`는 애플리케이션이 정의한 아웃고잉 포트를 구현한다.

```text
application/port/out
├── LoadAccountPort
└── UpdateAccountStatePort
```

나중에 SQL 데이터베이스로 변경해야 한다면 별도의 SQL 어댑터 패키지를 만든다.

```text
adapter/out/persistence/sql
├── SqlAccountPersistenceAdapter
├── JpaAccountEntity
└── SpringDataAccountRepository
```

SQL 어댑터도 기존의 `LoadAccountPort`, `UpdateAccountStatePort`를 구현한다. 두 어댑터가 같은 포트를 구현하므로 `SendMoneyService`는 데이터베이스가 Redis에서 SQL로 바뀌었다는 사실을 알 필요가 없다.

```text
SendMoneyService
    → LoadAccountPort / UpdateAccountStatePort
        → RedisAccountPersistenceAdapter  (교체 전)
        → SqlAccountPersistenceAdapter    (교체 후)
```

따라서 SQL 어댑터를 사용하도록 의존성 주입 설정을 변경하고 기존 Redis 어댑터 패키지를 제거하면 된다. 이때 `SendMoneyService`와 같은 애플리케이션의 핵심 로직은 변경하지 않는다.

> 패키지만 분리한다고 자동으로 교체가 쉬워지는 것은 아니다. 애플리케이션 코드가 Redis나 JPA 구현체를 직접 사용하지 않고, `application.port.out`의 인터페이스에만 의존해야 한다.

## 포트가 application 패키지와 같은 수준에 있지 않고 내부에 있는 이유

- 포트는 외부 기술이 정하는 규칙이 아니라, 애플리케이션이 외부에 통신하기 위해 정하는 규칙이므로 application 패키지 안에 둔다.
- 즉, 포트 자체가 애플리케이션의 일부이다.

## 표현력 있는 패키지 구조의 장점

- 완벽한 것은 없다. 하지만 적어도 표현력 있는 패키지 구조로 코드와 아키텍처 간의 차이를 줄일 수 있다??? (이부분은 이해도가 오른 다음 이해될 듯.)

# 이것이 유지보수 가능한 소프트웨어를 구축는 데 어떻게 도움이 될까? 

- 이번 장에서는 실제 코드 구조를 목표 아키텍처에 가장 가까운 헥사고날 아키텍처의 패키지 구조를 살펴봤음. 
- 패키지 이름에 `adapter`, `application`, `port`, `domain`과 같은 아키텍처 요소가 그대로 드러나므로 원하는 코드를 쉽게 찾을 수 있다. 덕분에 팀원끼리 구조를 설명하기 쉽고, 개발과 유지보수도 편해진다.
