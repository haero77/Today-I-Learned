# JPA/Spring Data 엔티티 공유와 실용적 매핑

```java
package io.reflectoring.reviewapp.domain;

import lombok.AllArgsConstructor;
import lombok.Getter;
import org.springframework.data.annotation.Id;

@Getter
@AllArgsConstructor
public class Book {

  @Id
  private Long id;
  private String title;
  private Long authorId;

  // *swipe* this is a very complex domain class ...
}
```

## 1. 도메인 모델에 영속성 애노테이션 허용 (실용적 타협)

- **원칙 vs 현실:** 순수 클린 아키텍처 관점에서는 도메인 엔티티가 영속성 프레임워크 (JPA, Spring Data)에 의존하면 안 되지만, 발표자는 도메인 패키지의
  엔티티 (`Book`)에 Spring Data의 `@Id` 같은 영속성 애노테이션을 직접 붙여 도메인 레이어와 영속성 레이어가 **동일한 객체를 공유**하는 방식을 예시로
  듭니다.
- **지름길 (Shortcut)의 인정:**

> *"이것은 일종의 지름길 (Shortcut)입니다. 비즈니스 코드에 영속성 코드 의존성을 두고 싶지 않겠지만, 초기 단계에서는 실용적인 선택이 될 수 있습니다."*



---

## 2. "처음부터 완벽한 경계를 둘 필요는 없다" ~

* **간단한 CRUD로 시작할 때:** 많은 유스케이스는 초기에 단순 CRUD 형태로 시작합니다. 이 단계에서 무리하게 매핑 계층 (Domain Model ↔ JPA
  Entity)을 나누면 보일러플레이트 코드와 유지보수 비용만 커집니다.
* **진화적 아키텍처 (Evolutionary Architecture):**
    1. **초기 단계 (No Mapping Strategy):** 도메인 엔티티를 영속성 계층에서도 그대로 사용하여 빠른 개발 속도를 확보합니다.
    2. **복잡도 증가 시점:** 유스케이스가 고도화되고 도메인 로직 내에 영속성 관련 관심사 (Lazy Loading, 더티 체킹 이슈 등)가 침투하기 시작하면, 그 시점에
       도메인 엔티티에서 애노테이션을 제거하고 **JPA 전용 엔티티와 도메인 모델을 분리한 뒤 매핑 (Mapping) 계층을 도입**합니다.

---

## 3. 클린/헥사고날 아키텍처의 비판과 트레이드오프 ~

* **매핑 오버헤드 (Mapping Overhead):** 클린/헥사고날 아키텍처에 대한 가장 큰 비판 중 하나는 "각 계층마다 모델을 따로 두고 매핑해야 해서 코드가 중복되고
  번거롭다"는 점입니다.
* **비즈니스 로직의 유무가 기준:**
    * 단순 데이터 전달 위주의 **단순 CRUD 애플리케이션이라면 굳이 엄격한 헥사고날/클린 아키텍처를 적용할 필요가 없습니다.**
    * 도메인 중심 아키텍처는 **중심부에 보호해야 할 '진짜 복잡한 비즈니스 로직 (Real business logic)'이 존재할 때** 비로소 진가를 발휘합니다.

---

## 요약

> **"처음부터 계층 간 엄격한 모델 분리/매핑을 강제하지 말고, 초기나 단순 CRUD 영역은 영속성 애노테이션을 공유 (No Mapping)하다가 도메인 로직이 복잡해지는
시점에 분리·리팩토링하라."**
