# 바운디드 컨텍스트의 핵심

> **_바운디드 컨텍스트를 해서 얻는게 뭘까? 왜 이 개념이 필요한 걸까? 결국 바운디드 컨텍스트는 무엇을 말하는 건가?_**

- 특정 단어(개념)가 의미하는 바가 하위 도메인마다 의미가 달라져, 의미의 구분없이 모호함이 생기게 됩니다.
- 이 모호함으로 인해 모델이 복잡해져서 유지보수성이 떨어지게 됩니다.
  - 유지보수성이 떨어진다는 것은 기능 확장이 어렵다는 것이고 서비스 경쟁력이 떨어지게 된다. (빠른 개발이 어렵고 빠른 개발을 하는 순간 안전성이 떨어짐)
  - (모델이 복잡해지는 이유: 여러 도메인의 요구사항이 한 모델에 섞이게되므로.)
- 이 모호함을 없애서 명확한 의미를 가질 수 있게 나눈 경계를 바운디드 컨텍스트라고 한다.
- 예를 들어볼게요.
- 상품이라는 단어, 개념이 있습니다.
- 근데 이 상품이라는 것은 하위 도메인마다 조금씩 그 의미가 달라집니다.
- 카탈로그 하위 도메인에서는 상품 설명, 가격 등 상품 자체의 정보를 의미하구요,
- 재고 하위 도메인에서는 창고에 있는, 셀 수 있는 물리적 개체를 의미합니다.
- 주문 하위 도메인에서는 실제로 주문한 주문 항목을 의미합니다.
- 그런데 이렇게 의미가 하위 도메인마다 달라지는데, 이걸 뭉뚱그려서 그냥 '상품'이라고 하면 의미가 모호해지는 거죠.
- 그래서, 이 모호함을 없애기 위해서, 각 하위 도메인마다 '상품'이라는 개념을 명확하게 구분해주는 경계를 설정하는데, 이 경계를 바운디드 컨텍스트라고 합니다.
- 카탈로그 바운디드 컨텍스트를 만들고, 재고 바운디드 컨텍스트를 만들고, 주문 바운디드 컨텍스트를 만드는 거죠.
- 각 바운디드 컨텍스트가 생겼으니, 그 안의 상품이라는 개념은 정확히 무엇을 의미하는지 명확해지겠죠. 
  - 의미가 명확하니까 역할이 확실하게 구분되고,
  - 역할이 확실하게 구분되니까 유지 보수성이 올라갈겁니다. 어느 기능이 어디에 있어야할지 명확해지니까 개발적으로 기능 확장이 수월해질테고, 용어 의미도 명확해지니까 팀원들간의 소통도 수월해질겁니다.
- 각 바운디드 컨텍스트 안에서는 용어의 의미가 명확하기 때문에, 팀원 모두가 동일한 의미로 소통할 수 있는 '유비쿼터스 언어'를 구축하는 기반이 됩니다." 이것이 곧 DDD를 하는 이유이기도 하고요.


- _(나중에 실 도입했던 예시로 변경)_ 

---

- "바운디드 컨텍스트는 모델의 언어적 모호성을 없애고, 명확한 의미를 가질 수 있도록 구분해주는 '경계' 입니다.
  - 이 경계를 통해 거대하고 복잡한 도메인 모델을 작고 관리 가능한 여러 모델로 나눌 수 있어, 결국 유지보수하기 쉽고 확장성 있는 소프트웨어를 만들 수 있습니다."
- 예를 들어 온라인 서점이라는 도메인에서의 '상품'이라는 개념을 예시로 들어보겠습니다. 
  - 온라인 서점 도메인에는 카탈로그, 재고, 주문 등 여러 하위 도메인이 있습니다.
  - 그런데, 카탈로그, 재고, 주문 등 각 하위 도메인에서 '상품'이라는 단어가 사용되지만, 그 의미는 서로 다릅니다.
    - 카탈로그에서의 상품은 상품명, 가격 등 상품 자체의 정보를,
    - 재고에서의 상품은 창고에 있는 물리적 개체를,
    - 주문에서의 상품은 주문 항목을 의미합니다.

---

- 거대한 모델을 만들 경우 유지보수의 어려움이 있음.
  - 여러 하위 도메인의 요구사항이 한 가지 모델에 섞이게 됨.
  - 같은 '상품'이라는 단어라도 비즈니스 맥락에 따라 전혀 다른 의미와 데이터를 갖게 되어 큰 혼란
- 하나의 거대한 모델을 갖는 것이 아닌, 
- 어떤 개념은, 컨텍스트가 주어질 때 그 의미가 명확해짐. 
  - 카탈로그 컨텍스트에서 '상품'은 고객에게 보여줄 정보(상품명, 가격, 이미지)를 의미합니다.
  - 재고 컨텍스트에서 '상품'은 창고에 있는 물리적 개체(재고 수량, 위치)를 의미합니다. 
  - 주문 컨텍스트에서 '상품'은 주문된 항목(주문 당시 가격, 수량)을 의미합니다.

# 하위 도메인과 바운디드 컨텍스트

좋은 질문입니다! '상품'이라는 개념이 하위 도메인과 어떻게 다른지 헷갈리는 것은 매우 자연스러운 현상입니다.

결론부터 말씀드리면, '상품'은 그 자체로 하나의 하위 도메인이라기보다는, **여러 하위 도메인에 걸쳐 각기 다른 의미와 역할을 가지는 핵심 '도메인 모델' 또는 '애그리거트(Aggregate)'**입니다.

제공해주신 자료에 따르면 '상품'은 어떤 컨텍스트(문맥)에 있느냐에 따라 완전히 다른 모습으로 모델링됩니다.

카탈로그 하위 도메인에서 '상품': 고객에게 보여주기 위한 정보가 중요합니다. 상품명, 가격, 상세 설명, 이미지 등이 핵심 데이터입니다.

재고 하위 도메인에서 '상품': 물리적인 재고 수량을 추적하는 것이 중요합니다. 따라서 '개별 객체를 추적'하는 것이 목적이 됩니다.

주문 하위 도메인에서 '상품': 주문의 일부인 '주문 항목(OrderLine)'으로 표현됩니다. 주문 당시의 가격과 수량이 중요합니다.

배송 하위 도메인에서 '상품': 고객에게 전달되어야 할 물리적인 물건을 의미합니다.

**_이처럼 '상품'은 단일 개념이 아니라, 각 하위 도메인(카탈로그, 재고, 주문 등)의 경계, 즉 바운디드 컨텍스트 안에서 각자의 목적에 맞게 다르게 정의되고 구현되는 것입니다._**

**_이것이 바로 바운디드 컨텍스트 개념의 핵심입니다. 하나의 거대한 '상품' 모델을 만드는 것이 아니라, 각 컨텍스트에 맞는 별도의 '상품' 모델을 만들어 모델의 의미를 명확하게 하고 복잡성을 낮추는 것이죠._**

# 9.1 도메인 모델과 경계

- 하위 도메인마다 같은 용어라도 의미가 다르고, 같은 대상이라도 지칭하는 용어가 다름.
- (1) **_하위 도메인마다 사용하는 용어가 다르기 때문에, 올바른 도메인 모델을 개발하려면 하위 도메인마다 모델을 만들어야함._**
  - 예) 카탈로그 도메인에서의 `상품`이, 검색 도메인에서는 `문서`로 불림. 
- (2) **_각 모델은 명시적으로 구분되는 경계를 가져서, 섞이지 않도록 해야함._**
  - _만약 여러 하위 도메인 모델이 섞이면?_ 
    - 여러 하위 도메인 모데이 섞이기 시작하면, **모델의 의미가 약해지고, 여러 도메인 모델이 서로 얽히게 됨.** 
    - 👉 하위 도메인별로 다르게 발전하는 요구사항을 모델에 반영하기 어려워짐 
    - (예: 재고 관리 도메인에서 상품의 개별 객체를 추적하기 위해 상품 모델에 일련번호 속성을 추가해야 하는데, 카탈로그 도메인에서는 상품 모델에 일련번호 속성이 필요하지 않은 거가 이 예시에 해당할까..?)

## 상품 예시

- 예를 들어 상품이라는 모델을 생각해보자.
- 카탈로그에서의 상품, 재고에서의 상품, 주문에서의 상품, 배송에서의 상품은 이름만 같지 실제로는 의미하는 바가 다름.
- 카탈로그에서의 상품은 상품명, 상품 가격 등 상품 정보가 위주이지만, 재고 관리에서의 상품은 개별 객체를 추적하기 위한 목적으로 상품을 사용. 
  - 👉카탈로그에서 상품은 물리적으로 한 개이지만, 재고에서는 여러 개 존재 가능
- 즉, 각 하위 도메인마다 용어는 같을지언정 그 의미가 다르므로, 이를 구분하기 위해 경계를 설정하고, 각 경계마다 모델을 별도로 정의하는 것이 필요하다!

## 바운디드 컨텍스트란?

- 모델은 특정한 컨텍스트 하에서 완전한 의미를 가짐.
    - 같은 상품이라도 카탈로그 컨텍스트와 재고 컨텍스트에서 의미가 서로 다름
- 이렇게 구분되는 경계를 갖는 컨텍스트를 **바운디드 컨텍스트(Bounded Context)**라고 함.
- (**_특정 도메인 모델이 명확하고 완전한 의미를 갖도록 구분하는 경계_**)



# 9.2 바운디드 컨텍스트(BC)

- 바운디드 컨텍스트는 모델의 경계를 결정.
- BC는 논리적으로 한 개의 모델을 가짐.
- BC는 용어를 기준으로 구분
  - 카탈로그 컨텍스트와 재고 컨텍스트는 서로 다른 용어를 사용하므로 이 용어 기준으로 BC 구분 가능.
- BC는 사용자에게 기능을 제공하는 물리적 시스템.
  - **_도메인 모델은 이 BC안에서 도메인을 구현한다._**

## 하위 도메인과 바운디드 컨텍스트의 관계

> 둘의 관계
이상적으로는 하나의 하위 도메인을 하나의 바운디드 컨텍스트로 개발하는 것이 가장 좋습니다.
> 
> 하지만 현실적으로 하나의 바운디드 컨텍스트 안에서 여러 하위 도메인을 개발할 수도 있습니다. 이 경우 가장 중요한 것은 각 하위 도메인의 모델이 서로 섞이지 않도록 명확하게 분리(예: 패키지 분리)하는 것입니다. 만약 모델이 섞이면 의미가 불분명해지고, 각 하위 도메인의 요구사항을 반영하기 어려워집니다.
> 
> 쉽게 비유하자면,
> 
> 하위 도메인 = 회사의 각 부서 (인사팀, 재무팀, 개발팀)
> 
> 바운디드 컨텍스트 = 각 부서가 사용하는 독립적인 업무 시스템 (인사 관리 시스템, 회계 시스템, 프로젝트 관리 시스템)
> 
> 각 부서(하위 도메인)마다 별도의 시스템(BC)을 사용하는 것이 이상적이지만, 작은 회사라면 하나의 시스템(BC) 안에서 여러 부서(하위 도메인)의 업무를 처리할 수도 있는 것과 같습니다.

>말씀하신 대로 **"바운디드 컨텍스트(BC)는 하위 도메인이 구현되는 시스템"**이라고 생각하시면 됩니다.
>
> 조금 더 덧붙여 설명해 드릴게요.
> 
> 하위 도메인은 '무엇을' 만들 것인가에 대한 논리적인 비즈니스 범위입니다. 예를 들어, '카탈로그', '주문'과 같은 비즈니스 영역을 나누는 것이죠.
> 
> 바운디드 컨텍스트는 그 하위 도메인을 '어떻게' 구현할 것인가에 대한 물리적이고 기술적인 경계입니다. 이 경계 안에는 표현, 응용, 도메인, 인프라 모든 영역이 포함된 하나의 독립적인 소프트웨어 시스템이 들어갑니다.


## 여러 하위 도메인을 하나의 BC안에서 개발 시 주의점

> 도메인, 하위 도메인, 바운디드 컨텍스트 
> - 도메인: 
>   - 전체 비즈니스 문제 영역 
>     - 온라인 서점
> - 하위 도메인: 
>   - 전체 비즈니스 문제 영역인 도메인을 논리적으로 나눈 작은 범위 
>     - 카탈로그, 재고, 주문, 결제, 배송
>     - 상품은 그 자체로 하나의 도메인이라기 보다는, 여러 하위 도메인에 걸쳐 각기 다른 의미를 갖는 도메인 모델 또는 **애그리거트**
> - 바운디드 컨텍스트: 
>   - 모델의 의미가 명확하게 유지되는 경계
>   - 솔루션을 구현하는 기술적인 범위. 하위 도메인이 구현되는 시스템
>   - 어떤 하위 도메인은 각각 별도의 BC로 구현될 수 있고, 어떤 하위 도메인은 하나의 BC안에서 함께 구현될 수 있음.

- **_하위 도메인의 모델이 섞이지 않게 한다._**
- 전체 하위 도메인을 위한 단일 모델을 만들고 싶은 유혹에 빠지기 쉬움.
  - 이런 유혹에 빠지면, 도메인 모델이 개별 하위 도메인을 제대로 반영 불가.
  - & 하위 도메인별로 기능 확장 불가. 서비스 경쟁력 떨어뜨림.
- 비록 한 개의 BC가 여러 하위 도메인을 포함하더라도 하위 도메인마다 구분되는 패키지를 갖도록 구현 해야함 -> 하위 도메인을 위한 모델이 뒤섞이지 않고, 하위 도메인 마다 BC를 갖는 효과 낼 수 있음.

# 9.3 바운디드 컨텍스트 구현

## 바운디드 컨텍스트는 모든 영역을 포함

- 바운디드 컨텍스트는 도메인 기능을 사용자에게 제공하는데 필요한 표현 영역, 응용 서비스, 도메인, 인프라스트럭처 영역을 모두 포함.
- 도메인 모델의 데이터 구조가 바뀌면 DB 테이블 스키마도 함께 변경해야하므로, **테이블도 바운디드 컨텍스트에 포함**됨.

## 바운디드 컨텍스트의 두 가지 개발 방식

1. 도메인 주도 개발
2. CRUD 방식
   - 서비스랑 DAO로 구성.
   - 도메인 기능이 서비스에 흩어지게 되지만, 도메인 기능 자체가 단순하면 CRUD 방식도 유지보수하는데 문제되지 않는다고 생각.

## 한 바운디드 컨텍스트에서 두 방식 혼합 사용 가능

- 예를 들어, CQRS 패턴을 이용해서 조회는 서비스-DAO 방식으로, 커맨드는 도메인 주도 개발 방식으로 구현하는 것도 가능.

## 각 바운디드 컨텍스트를 서로 다른 구현 기술 사용 가능

- 어떤 바운디드 컨텍스트는 
  - 웹 MVC: Spring MVC
  - 리포지터리 구현 기술: JPA/Hibernate
- 어떤 바운디드 컨텍스트는
  - Netty를 이용해서 REST API 제공.
  - 리포지터리 구현 기술: MyBatis
