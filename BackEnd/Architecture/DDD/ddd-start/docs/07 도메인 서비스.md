# 7.2 도메인 서비스

## 7.2.1 계산 로직과 도메인 서비스

### 응용서비스가 애그리거트에 도메인 서비스 전달

- 애그리거트 객체에 도메인 서비스를 전달하는 것은 응용 서비스 책임

### 도메인 서비스를 애그리거트에 주입하지 않기

- 도메인 객체는 필드로 구성된 데이터와 메서드를 이용해서 개념적으로 하나인 모델을 표현.
- 모델의 데이터를 담는 필드는 모델에서 중요한 구성 요소인데, discountCalculationService 필드는 **데이터 자체와는 관련 없다.** 다른 필드와 달리 DB 저장 대상도 아님.
- 또한, Order가 제공하는 모든 기능에서 discountCalculationService가 필요로 하는 것은 아님.
  - 일부 기능을 위해 굳이 도메인 서비스 객체를 애그리거트에 의존 주입할 이유는 없음.
  - 이는 프레임 워크의 기능을 사용하고 싶은 개발자의 욕심을 채우는 것에 불과.

### 트랜잭션 처리는 응용 서비스에서

- 도메인 서비스는 도메인 로직을 수행하지 응용 로직을 처리하지는 않음.
- 트랜잭션 처리와 같은 로직은 응용 로직이므로 도메인 서비스가 아닌 응용 서비스에서 처리.
  - 도메인 서비스 그 자체에서는 트랜잭션과는 관련없음. 


### 응용 서비스와 도메인 서비스를 어떻게 구분할까?

> p.240

- 해당 로직이 애그리거트의 상태를 변경하거나 애그리거트의 상태 값을 계산해는지 확인한다.
- 계좌 이체 로직 -> 계좌 애그리거트 상태 변경(계좌 2개 애그리거트 사용)
- 결제 금액 로직 -> 주문 애그리거트의 주문 금액 계산(쿠폰, 배송비, 포인트 .. 여러 애그리거트 협력 필요.)
- 이 두 로직은 각각 애그리거트를 변경하고 애그리거트의 값을 계산하는 도메인 로직 -> 도메인 로직이면서 한 애그리거트에 넣기에 적합하지 않으므로 두 로직은 도메인 서비스로 구현한다.

---

안녕하세요! DDD에서 응용 서비스와 도메인 서비스의 역할을 헷갈려 하시는 점, 충분히 이해됩니다. 핵심은 **"누가 비즈니스 규칙을 알고 있는가?"**에 있습니다.

사용자께서 지적하신 대로, 최종적인 상태 변경(예: 데이터베이스에 저장)을 호출하고 트랜잭션을 관리하는 것은 응용 서비스가 맞습니다. 하지만 상태를 어떻게 변경해야 하는지에 대한 **핵심 비즈니스 로직(도메인 지식)**은 도메인 서비스나 애그리거트가 담고 있습니다.

**_[핵심 구분: '무엇을' 할 것인가 vs '어떻게' 할 것인가]_**


간단히 말해, 두 서비스의 역할은 다음과 같이 나눌 수 있습니다.

응용 서비스 (Application Service): 무엇을 할지 결정하고 전체 과정을 조율합니다. 🧑‍✈️

사용자의 요청을 받아 도메인 객체(애그리거트, 도메인 서비스)를 찾거나 생성합니다.

도메인 객체에게 일을 시킵니다.

결과를 저장(트랜잭션 관리)하고, 외부 시스템에 알리는 등 흐름(flow)을 제어합니다.

비즈니스 규칙 자체는 모릅니다. "A 계좌에서 B 계좌로 돈을 보내라"는 요청을 처리할 뿐, '계좌 이체'라는 비즈니스 규칙의 상세 내용은 알지 못합니다.

도메인 서비스 (Domain Service): 특정 비즈니스 규칙을 어떻게 처리할지 알고 있습니다. 🧠

하나의 애그리거트가 책임지기 어려운 복잡한 계산이나 여러 애그리거트가 얽힌 비즈니스 로직을 수행합니다.

오직 도메인 로직 수행에만 집중하며, 트랜잭션이나 데이터베이스 저장 같은 기술적인 부분은 신경 쓰지 않습니다.

상태 변경이 필요할 때, 관련 애그리거트의 메서드를 호출하여 상태 변경을 '위임'합니다.

계좌 이체' 예시로 이해하기
'A 계좌에서 B 계좌로 10,000원을 이체한다'는 요구사항을 예로 들어보겠습니다.

1. 응용 서비스의 역할 (MoneyTransferApplicationService)
   "계좌 이체라는 작업 흐름을 지휘합니다."

```Java
public void transfer(String fromAccountId, String toAccountId, Money amount) {
    // 1. 트랜잭션 시작
    Account fromAccount = accountRepository.findById(fromAccountId); // 애그리거트 조회
    Account toAccount = accountRepository.findById(toAccountId);   // 애그리거트 조회

    // 2. 도메인 전문가(도메인 서비스)에게 비즈니스 로직 처리 위임
    moneyTransferDomainService.transfer(fromAccount, toAccount, amount);

    // 3. 변경된 애그리거트 상태 저장 (실제 DB 반영)
    accountRepository.save(fromAccount);
    accountRepository.save(toAccount);

    // 4. 트랜잭션 종료(커밋)
}
```

보시다시피, 응용 서비스는 transfer라는 비즈니스 로직을 직접 수행하지 않습니다. 단지 필요한 객체(계좌 A, 계좌 B)를 준비해서 도메인 서비스에 넘겨주고, 일이 끝나면 저장할 뿐입니다.

2. 도메인 서비스의 역할 (MoneyTransferDomainService)
   "'계좌 이체'라는 순수한 비즈니스 규칙을 수행합니다."

```Java
public void transfer(Account fromAccount, Account toAccount, Money amount) {
    // 실제 도메인 규칙을 여기서 처리!
    // 예: 출금 계좌의 잔액이 충분한지 확인
    if (fromAccount.getBalance().isLessThan(amount)) {
    throw new InsufficientBalanceException();
    }
    // 각 애그리거트에 상태 변경을 요청
    fromAccount.withdraw(amount);
    toAccount.deposit(amount);
}
```

도메인 서비스는 **'출금 계좌에서 돈을 빼고, 입금 계좌에 돈을 더한다'**는 핵심 비즈니스 규칙을 알고 있습니다. 이 로직은 하나의 Account 애그리거트에만 넣기엔 어색합니다. (A 계좌가 B 계좌의 상태까지 책임질 수는 없으니까요.) 그래서 별도의 도메인 서비스로 분리한 것입니다.

- **_계좌 이체 로직이 도메인 서비스인 이유_**
  - **하나의 애그리거트에 속하지 않는 로직**: '계좌 이체'라는 비즈니스 규칙은 A 계좌 애그리거트만의 책임도 아니고, B 계좌 애그리거트만의 책임도 아닙니다. A 계좌가 B 계좌의 내부 상태(deposit)를 직접 호출하는 것은 애그리거트의 독립성을 해치는 좋지 않은 설계입니다.
  - **여러 애그리거트의 협력 필요**: 이 로직은 A 계좌의 상태(잔액 감소)와 B 계좌의 상태(잔액 증가)를 모두 일관성 있게 변경해야 합니다. -> 일관성을 지키기 위한 도메인 규칙 -> 도메인 모델(도메인 서비스)가 담당.
- 이처럼 두 개 이상의 애그리거트가 얽혀있는 비즈니스 로직을 어떤 특정 애그리거트에 넣기 애매할 때, 그 로직을 수행하는 책임만 따로 분리하여 도메인 서비스로 만드는 것입니다.
- 도메인 서비스는 자체적으로 상태를 가지지 않고(stateless), 단순히 전달받은 애그리거트들을 이용해 특정 도메인 규칙을 수행하는 역할만 합니다. 아주 잘 이해하셨습니다! 👍
