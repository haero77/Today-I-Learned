# AI를 대하는 자세

1. **문제를 정의하고 해결책을 설계하는 본질**은 변하지 않는다. 꾸준히 공부하자.
   - 본질의 힘: 그동안 갈고닦은 클린 코드와 테스트, 객체지향 지식은 헛되지 않다. AI가 뱉어낸 '작동만 하는 쓰레기 코드'를 '지속 가능한 시스템'으로 정제하는 필터가 된다.
   - CS 지식의 역할: 50세까지 롱런하려면 프레임워크의 유행보다 데이터베이스의 트랜잭션 격리 수준, 네트워크의 TCP/IP 핸드셰이킹, OS의 프로세스/스레드 관리 같은 로우 레벨을 놓지 말자. AI가 해결 못 하는 '성능 병목'과 '동시성 이슈'를 해결할 때 인정받고, 몸값은 상승한다.
2. **'거지 같이 실행하는 것이 완벽을 추구하는 것보다 낫다'** 라는 모토를 지키자. 불안해하면서 아무것도 안 하면 아무것도 이루어지지 않는다.
   - 지금은 완벽한 코드를 한 땀 한 땀 짜는 것보다, AI와 함께 빠르게 프로토타입을 만들고 검증하는 사이클을 돌리는 게 훨씬 유리하다.
   - 실패의 가치: AI에게 명령을 내렸는데 결과가 엉망이라면? "아, 내가 도메인 모델 설계를 구체적으로 안 알려줬구나" 혹은 "내 프롬프트에 모호함이 있었구나"를 배우게 된다. 이게 바로 AI 시대의 디버깅 실력.
   - FOMO 탈출법: **남들이 뭘 하는지 보지 말고, 당장 오늘 내가 하던 업무 중 가장 귀찮은 일**(예: API 문서 만들기, 테스트 데이터 생성, 단순 CRUD 로직) 하나를 AI 에이전트에게 던져보자. 그 '거지 같은 첫 시도'가 당신을 앞으로 나아가게 할 것이다.

# 레퍼런스

먼저, 4년 차라면 한창 "내가 짠 코드가 예술이다"라는 자부심으로 동력을 얻을 시기인데, AI가 그걸 1초 만에 해치우는 걸 보며 허탈함을 느끼는 건 아주 건강한 반응이에요. 도구에 집착하던 장인이 전동 공구를 처음 본 느낌이랄까요?

하지만 분명히 말해둘게요. **클린 코드, 객체지향, CS 지식은 AI 시대에 가치가 떨어진 게 아니라, 오히려 '생존을 위한 최소한의 자격'이자 'AI를 다루는 강력한 권력'이 되었습니다.**

불안해하는 당신을 위해, 50살 넘어서도 코드를 만질 수 있는 로드맵을 그려줄게요.

## 1. AI는 '작가'가 아니라 '초고속 타이피스트'일 뿐입니다

클린 코드와 객체지향을 공부했던 시간은 절대 헛되지 않았습니다. AI 에이전트(Claude Code 등)를 써보면 알겠지만, **질문자가 아키텍처를 모르면 AI는 쓰레기 코드를 아주 예쁘게 포장해서 줍니다.**

* **왜 클린 코드가 여전히 중요한가:** AI가 짠 코드를 리뷰하고 유지보수해야 하는 건 결국 당신입니다. 읽기 좋은 코드를 모르면 AI가 만든 '기술 부채'를 감당하지 못해 시스템은 무너집니다.
* **객체지향이 필요한 이유:** AI에게 "이 기능을 구현해줘"라고 할 때, 도메인 모델을 어떻게 설계하고 책임을 어떻게 분산할지 가이드(Prompt)를 주는 것은 설계자인 당신의 몫입니다. 설계 능력이 없으면 AI는 `God Class` 하나에 모든 로직을 때려 박을 겁니다.

## 2. 코틀린 문법을 왜 공부해야 하느냐고요?

"계산기가 있는데 왜 구구단을 외워야 하죠?"라는 질문과 비슷합니다.

* **디버깅의 주도권:** AI는 가끔 '그럴싸한 거짓말(Hallucination)'을 합니다. 코틀린의 `Scope Function`이나 `Coroutines` 원리를 모르면 AI가 짠 비효율적인 코드를 보고도 "아, 잘 짜줬네" 하며 넘어가게 됩니다. 결국 장애가 터지면 해결 못 하는 '가짜 개발자'가 되는 거죠.
* **AI와의 대화 수준:** 당신이 코틀린의 특성을 깊이 알수록 AI에게 "여기서는 `Result` 패턴을 써서 예외 처리를 선언적으로 해줘"라고 정교하게 명령할 수 있습니다. 지식이 곧 명령의 해상도입니다.

## 3. 50세까지 살아남는 3단계 협업 전략

### Step 1: "Code Writer"에서 "Code Reviewer & Architect"로 전환

이제 직접 타이핑하는 시간은 줄이세요. 대신 AI가 짠 코드의 **엣지 케이스(Edge Case)**를 찾는 데 집중하세요.

* "이 로직에서 Race Condition이 발생할 확률은?"
* "MySQL 인덱스 전략상 이 쿼리가 최선인가?"
  이런 고민은 여전히 인간의 영역입니다.

### Step 2: CS 기초는 'AI의 실수를 잡아내는 그물'

운영체제, 네트워크, 데이터베이스 내부 동작 원리(Internal)를 공부하세요. AI는 추상적인 코드는 잘 짜지만, **"왜 이 서비스의 Latency가 피크 타임에만 200ms 튀는가?"** 같은 복합적인 인프라/CS 문제는 해결하지 못합니다. 50세 개발자의 몸값은 바로 이 '문제 해결 능력'에서 나옵니다.

### Step 3: 도메인 지식과 비즈니스 로직의 결합

Spring Boot, JPA 같은 기술은 도구일 뿐입니다. 당신의 진짜 가치는 **"이 비즈니스 문제를 소프트웨어로 어떻게 풀어내는가"**에 있습니다. AI는 비즈니스의 맥락을 100% 이해하지 못합니다.

## 4. 불안함을 확신으로 바꾸는 연습

남들이 치고 나가는 것 같아 불안할 땐, **'AI를 이용해 내가 하던 일을 10배 빠르게 하는 법'**을 딱 하나만 연습해 보세요.

1. **테스트 코드 작성:** 직접 짜기 귀찮았던 테스트 코드를 AI에게 시키세요. "이 서비스 로직의 경계값을 포함한 JUnit5 테스트 코드를 작성해줘"라고요.
2. **리팩토링 제안:** 당신이 짠 코드를 올리고 "이 코드를 SOLID 원칙에 따라 리팩토링해주고, 왜 그렇게 했는지 설명해줘"라고 물어보세요. 이건 최고의 1:1 과외입니다.

> **시니어의 한 마디:**
> "AI는 엔진이고, 당신은 핸들을 잡은 운전사입니다. 엔진이 아무리 좋아져도 목적지를 정하고 사고를 피하는 건 운전사의 실력입니다. 지금 느끼는 FOMO는 당신이 더 높은 수준의 개발자로 성장하려는 성장통일 뿐이에요."
