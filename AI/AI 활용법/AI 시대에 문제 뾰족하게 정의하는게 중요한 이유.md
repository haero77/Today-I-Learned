# AI 시대에 문제를 뾰족하게 정의하는 게 중요한 이유

## 핵심

AI가 코드를 작성하는 비용을 낮출수록, **무엇을 왜 바꿔야 하는지 결정하는 능력**이 더 중요해진다.

AI는 반복 코드 작성, 패키지 이동, DTO·Mapper·테스트 생성처럼 실행 방법이 명확한 작업을 빠르게 처리한다. 하지만 다음과 같은 판단은 사람이 먼저 내려야 한다.

- 지금 겪는 불편의 실제 원인은 무엇인가?
- 단순한 불편인가, 반복해서 문제를 만드는 구조적 결함인가?
- 어떤 의존성은 허용하고 어떤 의존성은 금지할 것인가?
- 이상적인 구조를 위해 어느 정도의 복잡성과 비용을 감수할 것인가?
- 기존 동작을 깨뜨리지 않고 어떤 순서로 바꿀 것인가?

즉, AI 시대의 개발자는 단순히 코드를 많이 작성하는 사람보다 **문제, 경계, 변경 순서, 완료 조건을 명확히 정의하는 사람**에 가까워진다.

## 모호한 요청이 위험한 이유

다음 요청은 목표가 너무 넓다.

> 이 프로젝트를 헥사고날 아키텍처로 리팩터링해 줘.

이렇게 요청하면 AI는 헥사고날을 형식적으로 적용하면서 불필요한 Port, DTO, Persistence Entity, Mapper를 대량으로 만들 수 있다. 구조는 복잡해졌지만 원래 문제가 무엇이었는지는 해결되지 않을 수도 있다.

반면 문제와 설계 선택을 구체적으로 정의하면 결과가 달라진다.

> 현재 `ReservationService`가 Controller DTO와 JPA Repository에 동시에 의존한다.
>
> - CUD 유스케이스는 Command와 입력 Port로 분리한다.
> - 애플리케이션 서비스는 영속성 출력 Port에만 의존한다.
> - 도메인 엔티티와 JPA 엔티티는 하나로 사용한다.
> - 단순 조회는 `Page<Projection>`을 프론트에 반환한다.
> - `application → adapter` 의존은 ArchUnit으로 금지한다.
> - 각 단계에서 기존 테스트가 통과해야 한다.

이 요청에는 다음 정보가 들어 있다.

1. 현재 문제
2. 바꾸려는 의존성
3. 의도적으로 허용할 결합
4. 과도한 분리를 피하기 위한 범위
5. 완료 여부를 판단할 검증 기준

AI는 이런 조건이 명확할수록 더 정확하고 작은 변경을 만들 수 있다.

## 단계적 리팩터링의 흐름

안전한 리팩터링은 한 번에 이상적인 구조로 갈아엎는 작업이 아니다. 다음 순서로 진행한다.

```text
증상 관찰
  ↓
구조적 원인 특정
  ↓
허용·금지할 의존성 결정
  ↓
작은 단위로 변경
  ↓
행위 테스트로 기능 회귀 방지
  ↓
아키텍처 테스트로 구조 회귀 방지
```

예를 들어 애플리케이션 서비스가 JPA Repository를 직접 참조하는 것이 문제라면, 전체 구조를 한 번에 바꾸지 않고 다음처럼 나눌 수 있다.

1. 현재 동작을 고정하는 테스트를 작성한다.
2. 도메인 Repository Port를 정의한다.
3. 기존 JPA 구현을 Persistence Adapter로 옮긴다.
4. 애플리케이션 서비스가 Port에 의존하도록 변경한다.
5. 기존 테스트로 기능이 유지되는지 확인한다.
6. ArchUnit으로 `application → adapter` 의존을 금지한다.

각 단계가 작기 때문에 문제가 생겨도 원인을 찾고 되돌리기 쉽다.

## 테스트도 두 종류가 필요하다

### 행위 테스트

기능이 이전과 동일하게 동작하는지 검증한다.

> 예약을 확정하면 상태와 재고가 올바르게 변경되는가?

### 아키텍처 테스트

코드의 의존성 방향이 다시 무너지지 않는지 검증한다.

> 애플리케이션 계층이 Adapter 구현체를 직접 참조하지 않는가?

행위 테스트만 있으면 기능은 유지되지만 구조가 다시 나빠질 수 있다. 아키텍처 테스트만 있으면 구조는 규칙에 맞아도 기능이 깨질 수 있다. 따라서 두 테스트가 함께 있어야 단계적 리팩터링을 안전하게 지속할 수 있다.

## 문제를 뾰족하게 정의하는 질문

AI에게 리팩터링을 맡기기 전에 최소한 다음을 답할 수 있어야 한다.

1. **증상은 무엇인가?**  
   변경할 때마다 어떤 코드가 함께 깨지거나 반복해서 수정되는가?

2. **원인은 무엇인가?**  
   책임이 섞였는가, 의존성 방향이 잘못됐는가, 모델의 경계가 부정확한가?

3. **이번 작업의 범위는 어디까지인가?**  
   해결하려는 문제와 의도적으로 손대지 않을 부분은 무엇인가?

4. **어떤 결합을 허용할 것인가?**  
   예를 들어 도메인 엔티티의 JPA 애너테이션과 애플리케이션 서비스의 `@Transactional`을 허용할 것인가?

5. **어떤 상태가 완료인가?**  
   통과해야 할 테스트와 금지해야 할 의존성은 무엇인가?

6. **어떤 순서로 바꿀 것인가?**  
   각 단계가 독립적으로 검증되고 되돌릴 수 있는가?

## 결론

AI는 구현 비용을 크게 낮춰 주지만, 무엇을 구현해야 하는지까지 자동으로 결정해 주지는 않는다. 문제가 모호하면 AI는 모호함을 코드와 구조의 양으로 채울 가능성이 있다.

따라서 AI 시대에는 다음 능력이 더욱 중요하다.

> 문제를 관찰하고 구조적 원인을 특정한 뒤, 허용할 경계와 완료 조건을 정하고, 검증 가능한 작은 단계로 리팩터링하는 능력

AI가 변경을 빠르게 수행할수록 개발자는 **코드를 직접 많이 쓰는 사람**에서 **올바른 변경을 정의하고 검증하는 사람**으로 이동한다.
