# 51. 인덱스가 필요한 이유

- 왜 필요한가?
  - 데이터가 많아질 수록 기존 쿼리가 느려짐. (수 초 ~ 수 분)
    - 👉  서비스 속도 하락(서비스 품질 하락)
    - 👉 고객 이탈률 증가 (이탈 위험) 
      - ⭐️ **반드시 해결해야하는 문제** ⭐️
  -  **_서비스 품질(속도) 유지, 향상을 위해 인덱스 필요._**

## 느린 검색의 원인: 풀 테이블 스캔(Full Table Scan)

> _인덱스가 없는 테이블에서 특정 데이터를 찾는 과정은, 비유하자면 100만 페이지짜리 거대한 책에서 특정 단어 하나를 찾기 위해, 책의 첫 페이지부터 마지막 페이지까지 한 장 한 장 넘겨보는 것과 같다._

- 데이터베이스는 item_name 컬럼에 '게이밍 노트북'이라는 값이 어디에 있는지 알 수 있는 아무런 '힌트'가 없음.
  - DB는 items 테이블 전체를 디스크에서 메모리로 읽어 들인 후, 첫 번째 행부터 마지막 100만 번째 행까지 차례대로 item_name 컬럼의 값을 비교함.

| item_id | seller_id | item_name | category | price | registered_date |
| --- | --- | --- | --- | --- | --- |
| 1 | 1 | 무선 기계식 키보드 | 전자기기 | 120000 | 2022-01-20 |
| 2 | 1 | 4K UHD 모니터 | 전자기기 | 450000 | 2022-02-15 |
| 3 | 2 | 프리미엄 게이밍 마우스 | 전자기기 | 80000 | 2021-11-10 |
| 4 | 3 | 관계형 데이터베이스 입문 | 도서 | 30000 | 2020-05-01 |

- 풀 테이블 스캔: O(n) 
- 데이터 건수에 정비례하여 쿼리 시간 증가. 
  - 최선의 경우 O(1): 찾는 데이터가 우연히 첫 번재 행에 있을 때 
    - 예) '무선 기계식 키보드'를 찾는 경우
  - 최악의 경우 O(n): 찾는 데이터가 마지막 행에 있을 때 또는 아예 존재하지 않을 경우 100만 번의 비교 연산 필요. 
- 👉 **_성능 문제 반드시 해결 필요_**

## 데이터 양에 따른 성능 저하

| 데이터 건수 | 총 데이터 크기(행당 1KB 가정) | 예상 응답시간 | 비고 |
| --- | --- | --- | --- |
| 100만 건 | 약 1GB | 수 초 (예: 0.2초 ~ 3초) | 디스크 I/O 속도에 따라 좌우되며, 메모리(버퍼 캐시)에 데이터가 일부라도 있으면 더 빨라짐 |
| 1,000만 건 | 약 10GB | 수 초 ~ 1분 내외 (예: 2초 ~ 30초) | 본격적으로 디스크 I/O 병목이 발생하기 시작하는 구간 |
| 1억 건 | 약 100GB | 수십 초 이상 (예: 20초 ~ 5분) | 다른 작업과 경합이 발생할 경우 응답시간은 예측하기 어려울 정도로 길어질 수 있음 |

_(기업용 SSD 디스크 기반, 한 행당 1KB 가정, 단일 쿼리 실행 시 다른 작업과의 리소스 경쟁이 없는 이상적인 상황 기준)_

- 정확한 응답 시간은 예측 불가
  - *응답시간은 데이터베이스 서버의 사양(CPU, 메모리, 디스크 I/O 성능), 환경 설정, 데이터의 한 행(Row)당 크기, 시스템의 현재 부하 등 수많은 변수에 따라 크게 달라짐.
- 위 표는 단순 참고용. 실 환경에서는 몇 배 이상 차이날 수 있음.
  - 실무에서는 본인 환경에 맞는 성능 테스트를 통해 성능 확인 필요.
  - 💡 **_실제로는 수 많은 요청을 동시에 처리하므로, 예를 들어서 10명의 사용자가 동시에 요청하면 풀 테이블 스캔도 10개가 동시에 발생가능. 이런 경우 성능은 훨씬 더 느려짐_**


## 실무 이야기 1: 사용자는 몇 초도 안 기다린다

> 페이징 로딩 속도에 관한 연구 (조금 오래된 연구이긴 함)
> - 모바일 페이지 로딩 속도 1초에서 3초로 늘어날 경우 이탈률 32% 증가
> - 모바일 페이지 로딩 속도 1초에서 5초로 늘어날 경우 이탈률 90% 증가
> 
> 👉 **_정리하면 웹 서비스는 3초 이내, 이상적으로는 1~2초 이내의 빠른 로딩 속도를 목표로 해야한다._**

- 오늘날의 사용자는 몇 초도 안 기다림.
  - 우리들만 봐도 1~2초 걸리면 바로 페이지 나감.
- 일반적인 서비스에서는 한 화면에서 여러 개의 테이블을 로드함.
  - 단순히 items 테이블 한 개만 조회하는 것이 아님.
  - 한 화면에서 다양한 테이블을 함께 조회하며, 이 테이블들을 모두 풀 테이블 스캔하면 서비스 느려지고, 사용자 이탈하게 됨.
- 서비스 계속 느려지고, 멈추고, 터지는 경우는 결국 문 닫게 된다!!
- ⭐️ **오픈하기 전에, 풀 테이블 스캔이 많이 일어나지 않게 잘 설계하는 것이 굉장히 중요하다!!** 
  - (예전에 멘토님이 배포 전에 애플리케이션에서 나오는 쿼리 실행계획 무조건 본다고 했는데 3년차된 이제야 좀 이해할 것 같음)


## 실무 이야기 2

- **풀테이블 스캔은 비용이 매우 높은 작업**
  - ⭐️ **_사용자들이 많이 쓰는 중요한 기능은 풀 테이블 스캔이 발생하면 안 된다!!_**
  - 서비스의 핵심 기능에서, 풀 테이블이 발생하지 않도록 설계하는 것이 필수.

### ⭐️ 풀 테이블 스캔 방지 설계

1. 인덱스 활용
   - **WHERE 절에 자주 사용되는 검색 조건 컬럼에는 인덱스 생성**하여 풀 테이블 스캔 방지.
2. 실행 계획 확인
   - ⭐️ **쿼리 실행 전 실행 계획을 확인하여 의도치 않은 풀 테이블 스캔이 발생하는지 반드시 점검**
3. 작업 시간 분리
   - 대용량 데이터에 대한 전체 스캔이 불가피한 통계/배치 작업이라면, 서비스 이용자가 적은 새벽 시간에 실행하는 것을 권장.


# 52. 인덱스 소개

- 데이터베이스의 인덱스(INDEX)는 이 책의 '찾아보기'와 정확히 동일한 역할임. 
- 인덱스는 특정 컬럼(들)의 데이터를 기반으로 생성되는, 원본 테이블과는 별개의 특수한 자료 구조. 
  - 인덱스는 지정된 컬럼(예: item_name )의 값과, 해당 값을 가진 실제 데이터 행의 위치(예: 주소값, 포인터, PK 값 등)를 한 쌍으로 저장함.
  - ⭐️ **가장 중요한 것은, 인덱스 내부의 데이터는 항상 정렬된 상태를 유지한다는 것.** (정렬이 되어있으니까 인덱스 기반으로 원본 레코드르 빨리 찾을 수 있음.)

## 인덱스 동작 원리

*실제 인덱스에는 PK 값이 들어있는 것이 아니고, PK 값이 들어있는 레코드의 위치(주소)가 들어있음.
