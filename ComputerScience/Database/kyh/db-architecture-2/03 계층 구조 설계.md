# 학습 목표

- 인접 리스트 모델로 계층 구조를 설계하는 방법
- 계층 구조 데이터를 조회할 때 발생하는 문제점
- CTE(Common Table Expression)를 활용한 재귀 쿼리
- 폐쇄 테이블 모델을 활용한 성능 최적화

# 계층 구조 설계가 필요한 이유

```sql
전자제품
├── 컴퓨터
│ ├── 노트북
│ ├── 데스크탑
│ └── 태블릿
├── 스마트폰
│ ├── 애플
│ └── 삼성
└── 가전제품
  ├── TV
  └── 냉장고
```

- 관계형 데이터베이스는 평면적인 테이블 구조를 가짐. 
- 행과 열로 이루어진 2차원 테이블에 트리 형태의 계층 구조를 어떻게 저장할지 학습해둬야함

# 인접 리스트 모델

- 인접 리스트 모델: 
  - 각 행이 **자신의 부모를 참조**하는 방식
  - 나의 부모가 누구인가? 라는 질문에 답하는 구조.
- 계층 구조를 데이터베이스에 저장할 때 가장 많이 쓰는 구조

## 인접 리스트 모델 아이디어

1. 각 노드는 자신의 부모 노드를 가리키는 왜래키를 갖는다
2. 최상위 노드(루트)는 부모가 없으므로 NULL을 가진다.

## 인접 리스트 모델 스키마

```sql
CREATE TABLE category
(
  category_id BIGINT       NOT NULL AUTO_INCREMENT,
  name        VARCHAR(100) NOT NULL,
  parent_id   BIGINT       NULL,
  PRIMARY KEY (category_id),
  FOREIGN KEY (parent_id) REFERENCES category (category_id)
);
```
- 쇼핑몰의 상품 카테고리를 인접 리스트 모델로 설계한 예시.
  - `category_id` : 카테고리의 고유 식별자
  - `name` : 카테고리 이름
  - `parent_id` : 부모 카테고리를 참조하는 외래 키. 자기 자신의 테이블을 참조하는 **자기 참조(Self-Referencing)** 관계이다.


## 기본 조회 쿼리 

### 루트 카테고리 조회

```sql
SELECT * FROM category WHERE parent_id IS NULL;
```
| category_id | name | parent_id |
| :--- | :--- | :--- |
| 1 | 전자제품 | NULL |
| 2 | 의류 | NULL |
| 3 | 식품 | NULL |

- parent_id가 NULL인 행이 루트 카테고리이다.

### 특정 카테고리의 직속 자식 조회

```sql
-- 전자제품(id=1)의 직속 자식 조회
SELECT * FROM category WHERE parent_id = 1;
```

| category_id | name | parent_id |
| :--- | :--- | :--- |
| 4 | 컴퓨터 | 1 |
| 5 | 스마트폰 | 1 |
| 6 | 가전제품 | 1 |

### 특정 카테고리의 부모 조회

```sql
-- 노트북(id=7)의 부모 조회
SELECT p.*
FROM category c
JOIN category p ON c.parent_id = p.category_id
WHERE c.category_id = 7; 
```

| category_id | name | parent_id |
|:------------|:-----|:----------|
| 4           | 컴퓨터  | 1         |


- 특정 카테고리 부모 조회 시 셀프 조인 사용.

## 인접 리스트 모델의 장점

1. 직관적인 구조: 부모-자식 관계를 외래 키 하나로 표현하므로 이해하기 쉬움.
2. 간단한 데이터 추가/수정/삭제: 노드 추가 또는 이동 작업이 단순함.
3. 저장 공간 효율성: 각 노드당 하나의 행만 저장하므로 저장 공간이 효율적.
4. 외래키 제약조건 활용: 외래키 제약조건 활용하여 참조 무결성 보장.

```sql
-- 새로운 카테고리 추가
INSERT INTO category (name, parent_id) VALUES ('게이밍노트북', 7);

-- 카테고리 이동 (노트북을 가전제품 아래로 이동)
UPDATE category SET parent_id = 6 WHERE category_id = 7;

-- 카테고리 삭제 (자식이 없는 경우)
DELETE FROM category WHERE category_id = 17;
```

## 인접 리스트 모델 한계

- 깊은 계층의 데이터를 한 번에 조회하기 어렵다.
- 즉, 직속 자식만 가져오는 것은 쉽다. 손자, 증손자까지 모든 자손을 조회하기는 어렵다.
- 예를 들어, "전자제품 카테고리 아래의 모든 하위 카테고리를 조회"하는 요구사항이 있다고 하자. 이걸 어떻게 한 번의 쿼리로 가져올까?
- 다음 섹션에서 계층 구조 조회의 어려움을 느껴보자.

# 계층 구조 조회의 어려움

```
전자제품 (id=1)
├── 컴퓨터 (id=4)
│   ├── 노트북 (id=7)
│   ├── 데스크탑 (id=8)
│   └── 태블릿 (id=9)
├── 스마트폰 (id=5)
│   ├── 애플 (id=10)
│   └── 삼성 (id=11)
└── 가전제품 (id=6)
    ├── TV (id=12)
    └── 냉장고 (id=13)
```
- 전자제품에 속한 모든 하위 카테고리를 조회하려면 어떻게 해야할까?
- 애플리케이션에서 반복 호출, JOIN을 사용한 고정 깊이 조회, UNION ALL을 사용한 조회 등이 있겠다.

## 자손 조회

### 방법1: 애플리케이션에서 반복 호출

```sql
-- 1단계: 루트 조회
SELECT * FROM category WHERE category_id = 1;

-- 2단계: 1단계 결과의 자식들 조회
SELECT * FROM category WHERE parent_id = 1;

-- 3단계: 2단계 결과의 자식들 조회
SELECT * FROM category WHERE parent_id IN (4, 5, 6);

-- 4단계: 3단계 결과의 자식들 조회 (결과가 없으면 종료)
SELECT * FROM category WHERE parent_id IN (7, 8, 9, 10, 11, 12, 13);
```

- 이 방법은 구현은 간단하지만, '계층의 깊이만큼' 데이터베이스를 호출해야한다.
- 즉, 계층이 깊어질수록 네트워크 비용이 높아지고, 성능 문제가 발생할 수 있다.

### 방법2: JOIN을 사용한 고정 깊이 조회

```sql
SELECT
  c1.category_id AS level1_id,
  c1.name AS level1_name,
  c2.category_id AS level2_id,
  c2.name AS level2_name,
  c3.category_id AS level3_id,
  c3.name AS level3_name
FROM category c1
LEFT JOIN category c2 ON c2.parent_id = c1.category_id
LEFT JOIN category c3 ON c3.parent_id = c2.category_id
WHERE c1.category_id = 1;
```

| level1_id | level1_name | level2_id | level2_name | level3_id | level3_name |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | 전자제품 | 4 | 컴퓨터 | 7 | 노트북 |
| 1 | 전자제품 | 4 | 컴퓨터 | 8 | 데스크탑 |
| 1 | 전자제품 | 4 | 컴퓨터 | 9 | 태블릿 |
| 1 | 전자제품 | 5 | 스마트폰 | 10 | 애플 |
| 1 | 전자제품 | 5 | 스마트폰 | 11 | 삼성 |
| 1 | 전자제품 | 6 | 가전제품 | 12 | TV |
| 1 | 전자제품 | 6 | 가전제품 | 13 | 냉장고 |

- 계층의 최대 깊이가 정해져있다면, JOIN을 사용하여 한 번의 쿼리로 조회할 수 있다. (위는 3단계까지 조회하는 예시)
- 한 번의 쿼리로 결과를 얻을 수 있지만, 몇 가지 문제가 있음.
  - 계층의 깊이가 고정되어있어야 한다.
  - 깊이가 늘어나면 JOIN도 늘어난다.
  - 결과가 중복으로 표시되어 처리가 필요하다

### 방법3: UNION ALL을 사용한 조회

```sql
-- 레벨 1: 전자제품 자신
SELECT category_id, name, parent_id, 1 AS level
FROM category
WHERE category_id = 1

UNION ALL

-- 레벨 2: 전자제품의 직속 자식
SELECT category_id, name, parent_id, 2 AS level
FROM category
WHERE parent_id = 1

UNION ALL

-- 레벨 3: 레벨 2의 자식들
SELECT c.category_id, c.name, c.parent_id, 3 AS level
FROM category c
WHERE c.parent_id IN (
  SELECT category_id FROM category WHERE parent_id = 1
);
```
| category_id | name | parent_id | level |
| :--- | :--- | :--- | :--- |
| 1 | 전자제품 | NULL | 1 |
| 4 | 컴퓨터 | 1 | 2 |
| 5 | 스마트폰 | 1 | 2 |
| 6 | 가전제품 | 1 | 2 |
| 7 | 노트북 | 4 | 3 |
| 8 | 데스크탑 | 4 | 3 |
| 9 | 태블릿 | 4 | 3 |
| 10 | 애플 | 5 | 3 |
| 11 | 삼성 | 5 | 3 |
| 12 | TV | 6 | 3 |
| 13 | 냉장고 | 6 | 3 |

- 각 레벨별로 쿼리를 작성하고 UNION ALL로 합치는 방법도 있다. 
- 그런데 이 방식도 JOIN을 사용한 고정 깊이 방식과 마찬가지로 계층의 깊이만큼 UNION을 추가해야하므로 유연하지 않다.

## 조상 조회

- 자손 조회하는 것 뿐만 아니라, 조상을 조회하는 것도 어렵다.
- 만약 '노트북' 카테고리의 모든 조상을 조회하려면 어떻게 해야할까?

### 조인 여러 번 사용

```
노트북 -> 컴퓨터 -> 전자제품
```

- 이것도 조인을 여러 번 사용해야한다. 

```sql
-- 노트북(id=7)의 조상들을 조회
SELECT
  c1.category_id AS id1, c1.name AS name1,
  c2.category_id AS id2, c2.name AS name2,
  c3.category_id AS id3, c3.name AS name3
FROM category c1
  LEFT JOIN category c2 ON c1.parent_id = c2.category_id
  LEFT JOIN category c3 ON c2.parent_id = c3.category_id
WHERE c1.category_id = 7;
```

| id1 | name1 | id2 | name2 | id3 | name3 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 7 | 노트북 | 4 | 컴퓨터 | 1 | 전자제품 |

### 특정 깊이까지만 조회 

- "전자제품 카테고리에서 2단계까지만 보여줘"라는 요구사항이 들어온다면?

```sql
-- 전자제품(id=1) 기준 2단계까지 조회
SELECT category_id, name, parent_id, 1 AS depth
FROM category
WHERE category_id = 1

UNION ALL

SELECT category_id, name, parent_id, 2 AS depth
FROM category
WHERE parent_id = 1;
```

| category_id | name | parent_id | depth |
| :--- | :--- | :--- | :--- |
| 1 | 전자제품 | NULL | 1 |
| 4 | 컴퓨터 | 1 | 2 |
| 5 | 스마트폰 | 1 | 2 |
| 6 | 가전제품 | 1 | 2 |

## 정리

| 방법           | 장점 | 단점 |
|:-------------| :--- | :--- |
| 애플리케이션 반복 호출 | 구현 간단 | 네트워크 비용, 성능 저하 |
| JOIN 고정 깊이   | 한 번의 쿼리 | 깊이 고정, 유연성 부족 |
| UNION ALL    | 레벨별 분리 가능 | 깊이 고정, 쿼리 복잡 |

- 지금까지 나온 방법들은 모두 계층의 깊이를 미리 알아야 하거나, 여러 번의 쿼리가 필요한 방식.
- 실무에서는 계층 구조 깊이는 가변적인 경우가 대부분. 
  - 즉, 위 방법들은 계층 깊이가 가변적일 때 적합하지 않음.
  - 그렇다고 애플리케이션에서 반복 호출하자니 네트워크 비용이 높아지고 성능이 저하됨.
- 이 문제를 해결하기 위해 SQL표준에 Recursive Query와 CTE(Common Table Expression)이 추가됨.

# CTE와 재귀 쿼리 1

> CTE: Common Table Expression

- 기존 계층 구조 문제점: **계층의 깊이가 가변적일 때 대응하기 어렵다**
- 실무 예시
  - 쇼핑몰 카테고리: 어떤 카테고리는 2단계, 어떤 카테고리는 5단계
  - 조직도: 부서에 따라 계층의 깊이가 다름
  - 댓글: 대댓글, 대대댓글... 깊이를 예측할 수 없음

## CTE란?

```sql
-- CTE(Common Table Expression) 문법
WITH cte_name AS (
-- CTE를 정의하는 쿼리
  SELECT ...
  )
-- CTE를 사용하는 메인 쿼리
SELECT * FROM cte_name;

-- 예시
WITH top_categories AS (
  SELECT * FROM category WHERE parent_id IS NULL
)
SELECT * FROM top_categories;
```

- 쿼리 내에서 임시로 사용할 수 있는 **이름 있는 결과 집합**
- WITH 절을 사용하여 정의

### 서브쿼리와의 차이점

- CTE 자체는 서브쿼리와 비슷해 보일 수 있지만, 몇 가지 장점이 있다.
- 쿼리의 가독성이 좋아진다.
- 같은 CTE를 여러 번 참조할 수 있다.
- **재귀 쿼리**를 작성할 수 있다.

## 재귀 CTE 문법

```sql
WITH RECURSIVE cte_name AS (
-- 기본 케이스 (Anchor Member): 재귀의 시작점
  SELECT ...
  UNION ALL
  -- 재귀 케이스 (Recursive Member): 자기 자신을 참조
  SELECT ... FROM cte_name WHERE ...
)
SELECT * FROM cte_name;
```

- 재귀 CTE는 **자기 자신을 참조하는 CTE**. 
- `WITH RECURSIVE` 키워드를 사용.
- 기본 케이스와 재귀 케이스를 구분하는 곳에 UNION 또는 UNION ALL을 적어줘야함. (문법상 필수)
- 쉽게 이야기해서 기본 케이스와 재귀 케이스의 결과를 합친다고 생각하면 됨.

## 재귀 CTE 구성과 실행

### 구성

1. **기본 케이스(Anchor Member)**: 재귀의 시작점. 처음 실행되는 쿼리.
2. **재귀 케이스(Recursive Member)**: CTE 자신을 참조하여 반복 실행되는 쿼리.

### 실행

1. 기본 케이스를 실행하여 초기 결과를 얻는다. 
2. 재귀 케이스를 실행하여 새로운 행을 얻는다. 
3. 새로운 행이 없을 때까지 2번(재귀 케이스)을 반복한다.
4. 모든 결과를 합쳐서 반환한다.

## 실전 재귀 CTE 예시

```sql
with recursive descendants as
                 (select c.category_id, c.name, c.parent_id, 1 as depth
                  from category c
                  where c.category_id = 1 -- 전자제품

                  union all

                  select c.category_id, c.name, c.parent_id, d.depth + 1
                  from category c
                         join descendants d on c.parent_id = d.category_id)
select *
from descendants;
```

- 핵심은 JOIN. 자신의 결과를 활용.
- 기본 케이스 실행 -> descendants에 전자제품이 들어감 -> 재귀 케이스 실행 -> descendants에 전자제품의 자식들이 들어감 -> 재귀 케이스 실행 -> 자식들의 자식들이 들어감 -> ... -> 더 이상 자식이 없을 때까지 반복. -> 지금까지 기본 케이스, 재귀 케이스에서 반환한 모든 데이터를 새로운 `descendants` 에 담아서 반환

# CTE와 재귀 쿼리 2

## 모든 조상 조회 

```sql
WITH RECURSIVE ancestors AS (
  -- 기본 케이스: 시작 노드 (노트북)
  SELECT category_id, name, parent_id, 1 AS depth
  FROM category
  WHERE category_id = 7
 
  UNION ALL
 
  -- 재귀 케이스: 부모를 찾아 올라감
  SELECT c.category_id, c.name, c.parent_id, a.depth + 1
  FROM category c
  JOIN ancestors a ON c.category_id = a.parent_id
)
SELECT * FROM ancestors;
```

| category_id | name | parent_id | depth |
| :--- | :--- | :--- | :--- |
| 7 | 노트북 | 4 | 1 |
| 4 | 컴퓨터 | 1 | 2 |
| 1 | 전자제품 | NULL | 3 |

### 조상 조회, 자손 조회 차이

- **자손 조회**: `c.parent_id = d.category_id` (자식의 `parent_id` 가 부모의 `id` 와 같음)
- **조상 조회**: `c.category_id = a.parent_id` (부모의 `id`(c.category_id) 가 자식의 `parent_id` 와 같음)

## 특정 깊이까지만 조회

```sql
WITH RECURSIVE descendants AS (
  SELECT category_id, name, parent_id, 1 AS depth
  FROM category
  WHERE category_id = 1
 
  UNION ALL
 
  SELECT c.category_id, c.name, c.parent_id, d.depth + 1
  FROM category c
  JOIN descendants d ON c.parent_id = d.category_id
  WHERE d.depth < 2 -- 2단계까지만 재귀
)
SELECT * FROM descendants;
```

| category_id | name | parent_id | depth |
| :--- | :--- | :--- | :--- |
| 1 | 전자제품 | NULL | 1 |
| 4 | 컴퓨터 | 1 | 2 |
| 5 | 스마트폰 | 1 | 2 |
| 6 | 가전제품 | 1 | 2 |

### 재귀 탈출 조건: 왜 `depth <= 2` 가 아닐까?

- 재귀 쿼리에서 `WHERE` 절은 '새로 만들어질 자식'이 아니라, **'현재 기준이 되는 부모(d)'**를 검사. 
- 즉, **"부모의 깊이가 얼마일 때 자식을 찾으러 갈 것인가?"**를 결정하는 멈춤 신호.
  - 첫 재귀쿼리에서, d.depth = 1임.

## 경로 표시

```sql
WITH RECURSIVE category_path AS (
  -- 기본 케이스: 루트 카테고리
  SELECT category_id, name, parent_id,
     CAST(name AS CHAR) AS path
  FROM category
  WHERE parent_id IS NULL
 
  UNION ALL
 
  -- 재귀 케이스: 경로에 현재 카테고리 이름 추가
  SELECT c.category_id, c.name, c.parent_id,
     CONCAT(cp.path, ' > ', c.name)
  FROM category c
  JOIN category_path cp ON c.parent_id = cp.category_id
)
SELECT category_id, name, path
FROM category_path
ORDER BY path;
```

## CTE 정리


### 장점

- **가변 깊이 지원**: 계층의 깊이가 얼마든 상관없이 모든 자손/조상을 조회 가능
- **단일 쿼리**: 여러 번의 데이터베이스 호출 없이 한 번의 쿼리로 결과를 얻을 수 있음.
- **표준 SQL**: SQL 표준 문법이므로 MySQL, PostgreSQL, SQL Server, Oracle 등 대부분의 RDBMS에서 사용 가능.
- **가독성**: 복잡한 계층 쿼리를 직관적으로 작성할 수 있음.
- **추가 정보**: 깊이(depth), 경로(path) 등의 정보를 함께 계산할 수 있다.

### 한계

- 대부분의 계층 구조 요구사항은 **인접 리스트 모델 + CTE 조합**으로 충분히 해결 가능. 데이터 양 매우 많아 조회 성능이 극도로 중요할 때는 폐쇄 테이블 사용.
