# 내용 요약

## 데이터 변경 이력 설계가 필요한 이유

- 데이터베이스 설계 시 '데이터 변경 이력'은 필수적인 요소다.
- 서비스 운영 중 "과거 가격 확인", "주소 변경 시점", "수정 주체" 등에 대한 질문에 답할 수 있어야 한다.
- 이력이 없으면 고객 클레임 처리, 감사 대응, 데이터 오류 원인 추적이 불가능하다.
- 가격 분쟁, 배송 오류, 금융 감사 등 실무에서 이력 부재로 인한 심각한 문제가 빈번히 발생한다.

## 이력이 없는 테이블 ~ 문제점 분석

- 기본 테이블 구조에서 `UPDATE` 를 수행하면 데이터가 덮어씌워져 과거 정보가 즉시 사라진다.
- "누가, 언제, 왜, 이전 값은 무엇인지"에 대한 질문에 전혀 답할 수 없다.
- 고객이 과거 시점의 데이터(예: 주문 당시 가격)를 근거로 문의할 때 확인 불가능한 심각한 운영 리스크가 있다.

## 변경 추적 컬럼 - 기본

- 테이블에 `created_at` (등록일), `created_by` (등록자), `updated_at` (수정일), `updated_by` (수정자) 컬럼을 추가.
- 데이터의 등록 및 수정 시점에 해당 정보를 함께 기록하여 "누가, 언제" 변경했는지 추적한다.
- 데이터 등록 시에도 `updated_at` 에 값을 채워넣는 것이 조회 및 정렬 로직 단순화에 유리하다.
- 이 방식은 이력이 중요하지 않은 마스터 데이터나 단순 내부 관리용 데이터에 적합함.
- "왜" 변경되었는지와 "이전 값"이 무엇인지는 여전히 알 수 없다.

## 변경 추적 컬럼 - 변경 사유

- "누가, 언제"를 넘어 "왜" 변경했는지 기록하기 위해 `change_type` (변경 유형)과 `change_reason` (변경 사유) 컬럼을 추가.
- `change_type` 은 시스템 처리와 검색 효율을 위해 코드로 표준화(예: `PRICE_CHANGE` , `STOCK_ADJUST` )하여 관리.
- `change_reason` 은 사람이 읽기 위한 구체적인 사유(예: 이벤트명, 단종 사유)를 텍스트로 기록.
- 변경 이유와 책임 추적이 가능해져 분쟁 해결에 도움이 되지만, 여전히 이전 값은 알 수 없음.

## 변경 추적 컬럼 - 감사(Audit) 컬럼

- 변경이 발생한 경로와 환경을 추적하기 위해 `source_system` (시스템 구분), `client_ip` (요청 IP) 컬럼을 추가.
- `source_system` 은 웹 관리자, API, 배치, 모바일 등 변경 요청의 출처를 구분하여 문제 원인을 빠르게 특정하는 데 사용.
- 보안 감사 및 시스템별 오류 추적에 유용함.
- 마이크로서비스 환경에서는 전체 흐름 추적을 위해 `request_id` 추가를 고려한다.

# 데이터 변경 이력 설계가 필요한 이유(데이터 변경 이력은 선택이 아니라 필수)

- 서비스가 성장하고 시간이 지나면 다음과 같은 요구사항이 발생
  - "이 상품의 가격이 '원래' 얼마였죠?"
  - "고객이 주소를 '언제' 변경했나요?"
  - "이 데이터를 '누가' 수정했나요?"
  - "작년 이맘때 회원 등급이 어떻게 되어있었나요?"
- 위 질문에 답할 수 없다면 다음과 같은 문제 발생.
  - 고객 클레임 처리 불가.
  - 감사에 대응 불가. (예: 금융서비스에서 감사관이 나옴)
  - 데이터 오류 발생 시 추적 불가.
- **실무 문제를 해결 하기 위해 데이터 변경 이력은 선택이 아니라 필수이다.**

## 이력이 없는 원본 테이블과 문제점

```sql
DROP TABLE IF EXISTS product;

CREATE TABLE product (
  product_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(200) NOT NULL,
  price INT NOT NULL,
  stock_quantity INT NOT NULL DEFAULT 0,
  status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE'
);

INSERT INTO product (name, price, stock_quantity, status)
VALUES ('스마트폰 케이스', 15000, 100, 'ACTIVE');

INSERT INTO product (name, price, stock_quantity, status)
VALUES ('무선 이어폰', 89000, 50, 'ACTIVE');

INSERT INTO product (name, price, stock_quantity, status)
VALUES ('노트북 파우치', 35000, 30, 'ACTIVE');

SELECT * FROM product;
```

| product_id | name | price | stock_quantity | status |
|------------|------|-------|----------------|--------|
| 1 | 스마트폰 케이스 | 15000 | 100 | ACTIVE |
| 2 | 무선 이어폰 | 89000 | 50 | ACTIVE |
| 3 | 노트북 파우치 | 35000 | 30 | ACTIVE |

- 상품을 생성했고, 상품 가격이 12,000원으로 변경되었다고 한다.

```sql
UPDATE product
SET price = 12000
WHERE product_id = 1;

SELECT * FROM product WHERE product_id = 1;
```

| product_id | name | price | stock_quantity | status |
|------------|------|-------|----------------|--------|
| 1 | 스마트폰 케이스 | 12000 | 100 | ACTIVE |


위 구조에서는 다음 질문에 답변 불가

- 질문 1: 누가 변경했나요?
- 질문 2: 언제 변경되었나요?
- 질문 3: 왜 변경되었나요?
- 질문 4: 이전 값은 얼마였나요?

# 변경 추적 컬럼 - 기본

```sql
DROP TABLE IF EXISTS product;

CREATE TABLE product (
  product_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(200) NOT NULL,
  price INT NOT NULL,
  stock_quantity INT NOT NULL DEFAULT 0,
  status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
  -- 변경 추적 컬럼
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  created_by VARCHAR(100) NOT NULL,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  updated_by VARCHAR(100) NOT NULL
);


INSERT INTO product (name, price, stock_quantity, status, created_by, updated_by)
VALUES ('스마트폰 케이스', 15000, 100, 'ACTIVE', 'admin_kim', 'admin_kim');
INSERT INTO product (name, price, stock_quantity, status, created_by, updated_by)
VALUES ('무선 이어폰', 89000, 50, 'ACTIVE', 'admin_lee', 'admin_lee');
INSERT INTO product (name, price, stock_quantity, status, created_by, updated_by)
VALUES ('노트북 파우치', 35000, 30, 'ACTIVE', 'admin_kim', 'admin_kim');


SELECT product_id, name, price, created_at, created_by, updated_at, updated_by
FROM product;
```

| product_id | name | price | created_at | created_by | updated_at | updated_by |
|------------|------|-------|------------|------------|------------|------------|
| 1 | 스마트폰 케이스 | 15000 | 2026-02-22 11:12:04 | admin_kim | 2026-02-22 11:12:04 | admin_kim |
| 2 | 무선 이어폰 | 89000 | 2026-02-22 11:12:05 | admin_lee | 2026-02-22 11:12:05 | admin_lee |
| 3 | 노트북 파우치 | 35000 | 2026-02-22 11:12:05 | admin_kim | 2026-02-22 11:12:05 | admin_kim |

- 이제 데이터 수정 시 아까의 질문에 답을 할 수 있게되었다.

```sql
UPDATE product
SET price = 12000,
  updated_by = 'admin_park'
WHERE product_id = 1;


SELECT product_id, name, price, created_at, created_by, updated_at, updated_by
FROM product
WHERE product_id = 1;
```

| product_id | name | price | created_at | created_by | updated_at | updated_by |
|------------|------|-------|------------|------------|------------|------------|
| 1 | 스마트폰 케이스 | 15000 | 2026-02-22 11:12:04 | admin_kim |2026-02-22 11:15:23| admin_park |

- 언제 등록되었나요? → 2026-02-22 11:12:04
- 누가 등록했나요? → admin_kim
- 언제 수정되었나요? → 2026-02-22 11:15:23
- 누가 수정했나요? → admin_park

## 변경 추적 컬럼 장점

1. 설계가 단순하다: 기존 테이블에 4개의 컬럼만 추가하면 됨.
2. 애플리케이션 코드가 단순하다: 등록과 수정 시 해당 컬럼만 채워주면 됨.

## 남은 문제

- **질문 1: 누가 변경했나요? 👉해결**
- **질문 2: 언제 변경되었나요? 👉해결**
- 질문 3: 왜 변경되었나요? 👉미해결
- 질문 4: 이전 값은 얼마였나요? 👉미해결

단순 변경추적 컬럼으로는 왜 변경되었는지와 이전값은 무엇이었는지를 알 수는 없다.

## 언제 사용하면 좋을까?

1. 이력이 중요하지 않은 마스터 데이터: 코드 테이블, 설정 테이블 등
2. 단순 운영 도구: 내부 관리용 데이터
3. 어드민 로그 정도의 용도: 누가 마지막으로 수정했는지만 알면 되는 경우

그러나 가격 변경, 주문 상태 변경, 회원 등급 변경 등 이력이 중요한 데이터는 이 방식만으로는 부족.

## 실무 가이드

- 실무에서 변경 추적 컬럼은 거의 모든 테이블에 다 적용한다. 
  - 그래서 실무의 테이블은 대부분 등록일, 등록자, 수정일, 수정자 컬럼을 포함한다.
- 데이터가 절대 변하면 안 되는 테이블의 경우에는 등록일, 등록자 컬럼만 포함하면 된다.

# 변경 추적 컬럼 - 변경 사유

## 문제 상황

- 상품 가격이 되었다. 담당자가 퇴사하거나 시간이 오래 지나면 왜 변경했는지 알 수가 없다.
  - "이 가격 변경은 할인 이벤트인가요, 원가 조정인가요?"
  - "언제까지 유효한 가격인가요?"
  - "누구의 승인을 받고 변경한 건가요?"
- 위 질문에 답하려면 변경 사유를 기록해야한다.

## 변경 사유 컬럼 추가

```sql

-- ## 변경 추적 컬럼 - 변경 사유

-- ### 변경 사유 컬럼 추가
DROP TABLE IF EXISTS product;

CREATE TABLE product (
  product_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(200) NOT NULL,
  price INT NOT NULL,
  stock_quantity INT NOT NULL DEFAULT 0,
  status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
  -- 기본 변경 추적 컬럼
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  created_by VARCHAR(100) NOT NULL,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  updated_by VARCHAR(100) NOT NULL,
  -- 변경 사유 컬럼
  change_type VARCHAR(50),
  change_reason VARCHAR(500)
);

-- ### 데이터 등록
INSERT INTO product (name, price, stock_quantity, status, created_by, updated_by, change_type, change_reason)
VALUES ('스마트폰 케이스', 15000, 100, 'ACTIVE', 'admin_kim', 'admin_kim', 'CREATE', '신규 상품 등록');

INSERT INTO product (name, price, stock_quantity, status, created_by, updated_by, change_type, change_reason)
VALUES ('무선 이어폰', 89000, 50, 'ACTIVE', 'admin_lee', 'admin_lee', 'CREATE', '신규 상품 등록');


SELECT product_id, name, price, change_type, change_reason, updated_by
FROM product;
```

| product_id | name | price | change_type | change_reason | updated_by |
|------------|------|-------|-------------|---------------|------------|
| 1 | 스마트폰 케이스 | 15000 | CREATE | 신규 상품 등록 | admin_kim |
| 2 | 무선 이어폰 | 89000 | CREATE | 신규 상품 등록 | admin_lee |


### 가격 변경 - 할인 이벤트

```sql
UPDATE product
SET price = 12000,
    updated_by = 'admin_park',
    change_type = 'PRICE_CHANGE',
    change_reason = '봄맞이 할인 이벤트 (2026-03-01 ~ 2026-03-31)'
WHERE product_id = 1;

SELECT product_id, name, price, change_type, change_reason
FROM product
WHERE product_id = 1;
```

| product_id | name | price | change_type | change_reason |
|------------|------|-------|-------------|---------------|
| 1 | 스마트폰 케이스 | 12000 | PRICE_CHANGE | 봄맞이 할인 이벤트 (2026-03-01 ~ 2026-03-31) |

```sql
SELECT product_id, name, status, change_type, change_reason
FROM product;
```

| product_id | name | status | change_type | change_reason |
|------------|------|--------|-------------|---------------|
| 1 | 스마트폰 케이스 | ACTIVE | STOCK_ADJUST | 월말 재고 실사 - 5개 파손 확인 |
| 2 | 무선 이어폰 | INACTIVE | STATUS_CHANGE | 제조사 단종 통보 |

## 변경 유형 표준화

| change_type | 설명 |
|-------------|------|
| CREATE | 신규 등록 |
| PRICE_CHANGE | 가격 변경 |
| STOCK_ADJUST | 재고 조정 |
| STATUS_CHANGE | 상태 변경 |
| INFO_UPDATE | 정보 수정 (이름, 설명 등) |
| PROMOTION | 프로모션 적용 |
| CORRECTION | 오류 정정 |

- 실무에서는 변경 유형(change_type)을 표준화해서 사용하는 것이 좋음.
- 변경 유형은 비즈니스마다 다르기 때문에 담당 부서에서 정해서 관리해야함.

## change_type을 사용하는 이유

- change_reason에 모든 내용을 적으면 될 것 같은데, 굳이 change_type을 따로 나누는 이유?
  - 👉데이터 활용과 검색의 효율성 때문.

---

1. 컴퓨터가 이해하기 쉬운 데이터 (구조화된 데이터)
   - change_reason은 사람이 읽기 위해 자유롭게 작성하는 텍스트.
   - PRICE_CHANGE 등 change_type은 약속된 코드를 사용하므로 시스템이 명확하게 구분 가능
2. 통계와 검색의 편리함.
   - 협업 부서에서 "자난달에 가격이 변경된 상품만 모두 뽑아주세요"라는 요청이 들어왔다고 할 경우, 
   - change_type이 없으면 `SELECT * FROM product WHERE change_reason LIKE '%재고%' OR change_reason LIKE '%할인%' OR change_reason LIKE '%단종%';`처럼 복잡하게 사용. 데이터 누락 위험성 존재.
   - change_type이 있으면 `SELECT * FROM product WHERE change_type = 'PRICE_CHANGE';`처럼 쿼리가 매우 단순해지고, 결과가 정확.

## 변경 사유 컬럼 장점

1. 변경 이유 알 수 있음: 왜 변경되었는지 기록이 남음.
2. 책임 추적 가능: 누가, 왜 변경했는지 명확함.
3. 분쟁 해결이 도움이 된다: "이 가격은 할인 이벤트 때문입니다"라고 근거 제시 가능.

# 변경 추적 컬럼 - 감사(Audit) 컬럼

- 최근 시스템은 누가, 언제, 왜 변경했는지 뿐만 아니라 더 상세한 정보 필요한 경우 많음.
- 예시:
  - "이 변경이 어떤 시스템에서 발생했나요? (API서버? 배치 서버? 관리자 화면?)
  - "어떤 IP에서 접속해서 변경했나요?"

## 감사 컬럼이 필요한 이유

현대 시스템은 하나의 데이터를 여러 경로에서 변경 가능

- 웹 관리자 화면(운영자가 직접 수정)
- API 서버(외부 연동을 통한 수정)
- 배치 시스템(정기 배치 작업)
- 모바일 앱(모바일에서의 수정)

👉 문제가 발생했을 때, "어디서 변경되었는지" 알아야 원인을 쉽고 빠르게 추적 가능.

## 감사 컬럼 추가

```sql
DROP TABLE IF EXISTS product;

CREATE TABLE product
(
    product_id     BIGINT PRIMARY KEY AUTO_INCREMENT,
    name           VARCHAR(200) NOT NULL,
    price          INT          NOT NULL,
    stock_quantity INT          NOT NULL DEFAULT 0,
    status         VARCHAR(20)  NOT NULL DEFAULT 'ACTIVE',
    -- 기본 변경 추적 컬럼
    created_at     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_by     VARCHAR(100) NOT NULL,
    updated_at     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    updated_by     VARCHAR(100) NOT NULL,
    -- 변경 사유 컬럼
    change_type    VARCHAR(50),
    change_reason  VARCHAR(500),
    -- 감사(Audit) 컬럼
    source_system  VARCHAR(50),
    client_ip      VARCHAR(50)
);
```
- `source_system` : 변경이 발생한 시스템 (예: WEB_ADMIN, API, BATCH,  MOBILE 등)
- `client_ip` : 요청이 발생한 클라이언트 IP 주소

### 데이터 등록 - 웹 관리자 화면
 
```sql
INSERT INTO product (name, price, stock_quantity, status,
                     created_by, updated_by,
                     change_type, change_reason,
                     source_system, client_ip)
VALUES ('스마트폰 케이스', 15000, 100, 'ACTIVE',
        'admin_kim', 'admin_kim',
        'CREATE', '신규 상품 등록',
        'WEB_ADMIN', '192.168.1.3');


SELECT product_id, name, price, source_system, client_ip
FROM product;
```

| product_id | name | price | source_system | client_ip |
|------------|------|-------|---------------|-----------|
| 1 | 스마트폰 케이스 | 15000 | WEB_ADMIN | 192.168.1.3 |

- `source_system` 컬럼에 `WEB_ADMIN` 값으로 등록된 것을 확인 가능.
- `client_ip` 를 통해 어떤 IP를 통해 들어온 요청인지 확인 가능.

### 데이터 수정 - API 연동

> 외부 시스템에서 API를 통해 가격을 변경하는 상황

```sql
UPDATE product
SET price         = 13000,
    updated_by    = 'partner_api',
    change_type   = 'PRICE_CHANGE',
    change_reason = '외부 프로모션 가격 동기화',
    source_system = 'API',
    client_ip     = '123.123.123.123'
WHERE product_id = 1;


SELECT product_id, name, price, source_system, client_ip, change_reason
FROM product
WHERE product_id = 1;
```
| product_id | name | price | source_system | client_ip | change_reason |
|------------|------|-------|---------------|-----------|---------------|
| 1 | 스마트폰 케이스 | 13000 | API | 123.123.123.123 | 외부 프로모션 가격 동기화 |

- `source_system` 컬럼에 `API` 값으로 등록된 것을 확인 가능.
- `client_ip` 를 통해 어떤 IP를 통해 들어온 요청인지 확인 가능.

### 데이터 수정 - 배치 작업

> 야간 배치 작업에서 재고를 조정하는 상황

```sql
UPDATE product
SET stock_quantity = 85,
    updated_by     = 'batch_system',
    change_type    = 'STOCK_ADJUST',
    change_reason  = '야간 재고 동기화 배치',
    source_system  = 'BATCH',
    client_ip      = '10.0.0.5'
WHERE product_id = 1;

SELECT product_id, name, stock_quantity, source_system, client_ip
FROM product
WHERE product_id = 1;
```

| product_id | name | stock_quantity | source_system | client_ip |
|------------|------|----------------|---------------|-----------|
| 1 | 스마트폰 케이스 | 85 | BATCH | 10.0.0.5 |

## source_system 표준화

| source_system | 설명 |
|---------------|------|
| WEB_ADMIN | 웹 관리자 화면 |
| WEB_USER | 웹 사용자 화면 |

# 과거 데이터 추적

- `질문 4: 이전 값은 얼마였나요?`는 어떻게 해결할까?
- 질문 4는 다음 3가지 문제를 먼저 해결해야함.
  - 1. 마지막 변경 정보만 남음: 이전 변경 이력이 덮어씌워짐.
  - 2. 이전 값을 알 수 없다: 변경 전 가격, 변경 전 재고 등을 알 수 없다.
  - 3. 변경 횟수를 알 수 없다: 몇 번 변경되었는지 파악할 수 없음.
- 현재 테이블에 컬럼을 추가하는 방식으로는 과거 데이터를 보존 불가능.

# 추적용 요청 ID(correlation_id) 

- 마이크로서비스 아키텍처 사용한다면 추적용 요청 ID(request_id)추가를 고려하자.
- 하나의 사용자자 요청이 여러 서비스를 거칠 대, 동일한 request_id를 사용하면 전체 흐름을 쉽게 추적 가능.
- 예를 들어, 고객이 "주문은 했는데 재고가 안 빠졌어요"라고 문의가 들어왔다고 하자. 이 경우 주문 시스템의 로그에서 `request_id` 를 찾으면, 동일한 ID로 상품 시스템, 결제 시스템, 배송 시스템의 로그를 모두 찾을 수 있다.

| updated_by | VARCHAR(100) | 마지막 수정자 |

- **사용 상황**: 거의 모든 테이블에 기본으로 추가하는 것이 좋음. "최소한의 추적"이 필요한 모든 곳에 사용.

## 변경 사유 컬럼

| 컬럼명 | 타입 | 설명 |
|--------|------|------|
| change_type | VARCHAR(50) | 변경 유형 (PRICE_CHANGE, STATUS_CHANGE 등) |
| change_reason | VARCHAR(500) | 변경 사유 (자유 텍스트) |

- 사용 상황: 
  - 변경 이유가 중요한 데이터에 추가. 
  - 가격, 상태, 등급 등 비즈니스적으로 의미 있는 변경에 사용.

## 감사(Audit) 컬럼

| 컬럼명 | 타입 | 설명 |
|--------|------|------|
| source_system | VARCHAR(50) | 변경 발생 시스템 |
| client_ip | VARCHAR(50) | 클라이언트 IP |

- 사용 상황: 여러 시스템에서 데이터를 변경하는 경우, 보안 감사가 필요한 경우에 사용.
